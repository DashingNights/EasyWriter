## 1. Goal and scope

One typed **command registry** in the renderer is the only way to *do* anything in DAF Writer by program: drafts, folders, tags, threads, document edits, board and canvas items, export preview, push preparation, and later `plan.*` / `flow.*`. Three callers share it, and a fourth is planned:

| Caller | Entry | Transport |
|---|---|---|
| The UI (Ctrl+Space palette; later sidebar / toolbar where convenient) | `tools.js` entries with a `command` field call `invoke` | in-process |
| Scripted acceptance (`npm run smoke`) | `window.__agent.script(steps)` | `executeJavaScript` from main (existing smoke path) |
| External agents (Claude Code / Claude Desktop via MCP, shell scripts) | `bin/daf-agent.js` = MCP server on stdio + CLI, talking to the running app over a local pipe | pipe → main → `webContents.send` → renderer |
| Local multimodal assistant (future, planning only, §13) | in-app client calling `invoke` with `source: 'agent:assistant'` | in-process (the model runs in a local `llama-server` that main starts, §13.2) |

In scope: the registry and executor, the initial catalogue (§7), approval UX, the pipe transport and bridge, hidden headless runs, audit, the shared `fileFamily` helper in main and the data-model conventions every new system follows (§4.3). Out of scope: the Gantt/Kanban and flowchart features themselves (their plans register commands here), auditing raw UI clicks, MCP resources/prompts, a TCP/HTTP server.

Invariants that never move:
- The forum is never auto-submitted: there is no `push.submit`; `forumPush` (main.js:318-359) only fills the reply editor and the human confirm before a push stays (actions.js:644-648).
- Renderer stays `contextIsolation: true, sandbox: true, nodeIntegration: false` (main.js:413-419). Agent input is JSON data, never code: no `eval`, no `executeJavaScript` with agent strings, no `new Function`.
- Destructive operations are trash moves, edits under undo (the document's or a namespace's own stack), or settings writes whose result carries what they removed (`tags.remove`); agents get them only after an in-app confirmation shown as an agent request (§5.1), asked on every call (no session-wide approval), never through the user's own dialog slot. §5.2 defines what counts as destructive for every namespace.
- One writer: every write goes through the running app and main's serialized queue (main.js:49-76). The bridge never touches files.
- **Agent actions are precise edits** (user decision, 2026-10-06): every command changes the smallest addressable unit (one entry, one item, one block, or one field set) and never rewrites a whole document, board or list (§4.3 #11).
- **Commands are gated like the controls**: a command declares the preconditions the UI uses to show or enable its control, and the executor checks them, with the same functions, before it runs (§3.7).
- Agent default is **off** (`settings.agent.enabled = false`).

## 2. User stories

1. As the author, I press Ctrl+Space, type "tag draft", pick a draft status — the same command an agent would call, with the same validation.
2. As the author, I say to Claude Code "turn my notes.md into a draft in the Level Design thread" — the agent creates a draft, inserts Markdown, and I see it appear in the sidebar without losing my caret or my undo history.
3. As the author, while I type, an agent fixes a heading two blocks above; its change is one Ctrl+Z step and never moves my selection or scroll.
4. As the author, an agent asks to delete a draft: a small non-modal card at the bottom right says "Claude Code wants to delete 'Week 3 notes' (trash)". Allow / Deny. The next delete asks again. My keyboard shortcuts keep working while it waits.
5. As the author, I can see "Agent: claude-code" in the status bar while a connection is open, and disconnect it from there.
6. As an agent, I can list the drafts of a thread, read a draft as Markdown or outline, find a phrase, and replace that block, with a revision token that still works if the author typed in the meantime.
7. As an agent, I can insert a whiteboard, add shapes and text items by JSON, and render the board to a PNG to check what I drew.
8. As an agent, I can prepare a push (fill the forum reply box) but never submit: the author presses Submit.
9. As a test, `npm run smoke -- --script test/smoke/agent-basic.json` runs a scripted sequence against a throwaway data directory and fails on any unexpected result or on a doc command that made more than one undo step.
10. As the Gantt/Kanban plan, I register `plan.*` commands with `define()` (persisting through my own `api.plans.*`) and get MCP tools, dry run, audit and approval for free.
11. As an agent, a call the UI would not offer (Unpush on a draft that was never pushed, Fit height on a canvas) fails with `precondition_failed`, naming the requirement and how to meet it; I fix my state and retry.

## 3. Concepts and data model

### 3.1 Command definition

Catalogue modules are pure ES modules (`src/app/commands/*.mjs`) that import only import-free helpers; everything with DOM, React, TipTap or `window.api` reaches a command through `ctx`. This keeps the catalogue importable by `node --test`.

```js
// src/app/commands/drafts.mjs
import { ID } from './schema-defs.mjs';
export const defs = [define({
  id: 'drafts.setTag',                 // /^[a-z]+(\.[a-zA-Z]+)+$/, ≤ 48 chars; MCP name = id with '.' → '_'
  title: 'Set the status tag of a draft',
  group: 'drafts',
  risk: 'write',                       // 'read' | 'write' | 'destructive' | 'approval'
  undo: 'none',                        // 'doc' (TipTap history) | 'own' (the namespace ships <ns>.undo/redo) | 'none'
  headless: true,                      // false: needs a visible window or a native dialog; denied for agent:* and hidden runs
  slow: false,                         // true: 300 s timeout instead of 60 s
  needs: [],                           // preconditions: gate ids from src/app/gates.mjs (§3.7), the same ones the UI checks
  args: { type: 'object', required: ['draftId', 'tagId'], additionalProperties: false,
          properties: { draftId: ID, tagId: { type: ['string', 'null'] } } },
  result: { type: 'object', required: ['draftTags'], properties: { draftTags: { type: 'object' } } },
  examples: [{ args: { draftId: '0b2c8f0e-1c4e-4f8a-9d6a-2b7f3c9e1a55', tagId: 'done' } }],
  plan: (ctx, a) => ({ settings: { draftTags: tagDraft(ctx.state.settings, ctx.state.drafts, a.draftId, a.tagId) } }),
  run: async (ctx, a) => ({ draftTags: (await ctx.actions.setDraftTag(a.draftId, a.tagId)).draftTags }),
})];
```

- `define(def)` validates the shape at module load (ids unique, regex, enums, schemas well-formed, every `needs` entry names a gate; `headless` defaults to `true`, `slow` to `false`, `needs` to `[]`) and returns `def`; `src/app/commands/catalogue.mjs` concatenates every module's `defs` into `CATALOGUE` and exports `$defs = { ID, PATH, URL, TAG_ID, ITEM, … }` (§3.5).
- `ctx = { state, editor, api, actions, board, source, policy, signal, ask(title, description), emit(event) }`: `state` = store state, `editor` = `state.editor`, `api` = `window.api`, `actions` = the `actions.js` module, `board` = `canvasEditor.get()?.board ?? activeBoard.get()`, `plans` = the `src/app/plans.js` module once the Gantt plan lands (its `dispatch`, `openPlan`, chart helpers), `flows` = the `src/app/flows.js` store (flowchart plan §4: records, `save`, `undo/redo`, `insertFlowchart`), `signal` = `AbortSignal` of the call, `ask` = the agent confirm (§5.1).
- Two styles:
  - **builder**: `plan(ctx, args)` returns `{tr}` (a ProseMirror transaction built from `editor.state`) or `{settings: patch}`. The executor applies it. Dry run is free (§3.3).
  - **imperative**: `run(ctx, args)` only (`drafts.open`, `push.prepare`, `forum.login`, `threads.discover`). Dry run returns `{simulated: false, title, args}`.
  - A command may have both: `plan` for dry run, `run` for the real thing (used when `run` must await I/O).
  - **own-store namespaces** (`undo: 'own'`, e.g. `plan.*`): `plan(ctx, args)` returns the would-be record (the dry-run result) and `run` calls the namespace's own writer (`ctx.plans.dispatch(id, args, {source})`), which applies, persists and keeps that namespace's undo stack (Gantt plan §8.2).
- `examples[]` are `{args, dryRun?}` pairs validated by the contract test; every command has at least one.
- Categories (tool discovery, §7 **commands**, §13.2 Tool calls): `src/app/commands/tool-sets.mjs` maps `group` to a category. Groups app, ui, audit, settings, tool, batch and commands → `app`; drafts, tags, folders, threads → `drafts`; export, push, forum → `export`; every other group is its own category (`doc`, `board`, `history`, later `plan`, `flow`, `research`, `calc`). There is no new `define` field: a new namespace adds one about-line to `CATEGORIES`, and the contract test checks that every command's category has one. Titles are at most 90 characters (contract test), because a tool's description in the model form is its title alone.

### 3.2 Envelope, result, errors

```json
{ "id": "doc.replace", "args": { "path": [3], "content": { "markdown": "## Week 3" } },
  "source": "agent:claude-code", "dryRun": false, "ifRev": 412, "timeoutMs": 60000 }
```
`source ∈ 'ui' | 'palette' | 'smoke' | 'agent:<name>'` (`<name>` = `/^[a-z0-9][a-z0-9_-]{0,31}$/`). `dryRun`, `ifRev`, `timeoutMs` are envelope fields, never inside `args`.

Result:
```json
{ "ok": true, "result": { "paths": [[3]] }, "draftId": "0b2c…", "rev": 413, "undoSteps": 1, "ms": 7, "dryRun": false }
{ "ok": false, "error": { "code": "stale", "message": "block [3] was deleted after rev 412", "data": { "rev": 420 } } }
```
Codes: `unknown_command, invalid_args, precondition_failed, denied, cancelled, stale, busy, not_found, already_exists, refused, failed, timeout, unauthorized, too_large`. `invalid_args.data = {path, message, expected}` (`path` = JSON pointer into `args`, `expected` = the schema at that pointer, `$ref` resolved), so an agent can correct the call. `precondition_failed.data = {failed: [{gate, message, fix}]}`: every gate (§3.7) that does not hold, with what satisfies it; nothing was written. `refused.data = {code, …}`: a namespace rule about the arguments said no (Gantt: `cycle`, `parent_dep`, `exists`, `tag_taken`, `unmapped_column`, `bad_unit`; flowchart: `dangling`, `unsupported_format`, `parse_error {line, col}`, `layout_failed`); namespaces add no top-level codes. `denied.data = {reason: 'policy'|'headless'|'user'|'timeout'}`.

### 3.3 Executor `invoke(req)` (`src/app/commands.js`)

1. **Queue.** Every non-`ui` invocation joins one renderer promise chain (`invokeChain`, like `saveChain` actions.js:314), whatever its connection: at most one external/smoke command runs at a time; main's connections are behind the same queue (a second connection's call waits, it does not run in parallel). `ui`/`palette` calls run at once (they are the user).
2. **Lookup** → `unknown_command`.
3. **Validate** `args` against `def.args` (`src/app/schema.mjs`, §8) → `invalid_args`.
4. **Revision** (§3.4): with `ifRev`, resolve every `PATH` argument as of that revision and map it forward; a mapped block that no longer exists → `stale`. Without `ifRev`, paths mean "now".
5. **Preconditions** (§3.7): every applicable gate of `def.needs`, on the subject it reads → `precondition_failed` listing every failed gate. Runs on dry runs too, and before any ask, so the user is never asked to approve a call that cannot run.
6. **Policy** (§5.2): `read` always; `write` if `policy.write`; `destructive`/`approval` → `ask` (§5.1) on every call (nothing is remembered); `headless:false` with `source` `agent:*` or a hidden window → `denied{headless}`.
7. **Busy**: for a doc write targeting a board node, `busy` if that board's live `Board` has `gesture` or `editingId` (whiteboard.js:692-695); for any doc write, `busy` if `canvasEditor.get()` is editing the target node. Agent writes never call `finishBoardEdits()`; other boards are writable. The user wins. Checked after the ask, because the user may start a gesture while the card waits.
8. **Settings writes** re-read `state.settings` inside the serialized section right before building the patch (no stale read across awaits).
9. **Doc writes**: at most one transaction per command. The executor dispatches `closeHistory(tr)` before and sets `closeHistory` on the command's transaction, dispatches with `editor.view.dispatch(tr)` (never `editor.chain().focus()` for `agent:*`/`smoke`; no `scrollIntoView`), leaves the selection untouched unless the command is `ui.*`. It measures `undoDepth` before/after and reports `undoSteps`; the smoke script asserts `undoSteps ≤ 1` for `undo: 'doc'` commands.
10. **Dry run** (`dryRun: true`): builder commands apply `editor.state.apply(tr)` without dispatching, or compute the settings patch (own-store commands return their `plan` result, §3.1); result `{ok: true, dryRun: true, result, diff}` with `diff = {from, to, before: outline[], after: outline[]}` — `from/to` = the union of the ranges the transaction's step maps change, `before/after` = `outline()` entries (§3.5) of the top-level blocks touching that range in the old / new doc. Nothing is written, no event is emitted, no audit line beyond `dryRun: true`.
11. **Timeout / cancel**: `timeoutMs` default 60 000, `slow` commands 300 000, capped at 600 000; `ctx.signal` aborts on timeout or on the transport's cancel (§4.4); result `timeout` / `cancelled`. Imperative commands that await the user (`ask`, `forum.login`) check the signal.
12. **Result** stamped with `draftId`, `rev`, `ms`; **audit** (§4.2) and **events** (§3.6) emitted.

### 3.4 Revision and position mapping

- `state.rev` (store.js) is a monotonic integer that never resets: `mountEditor` (actions.js:267-292) does `rev++` and clears the mapping log; every `docChanged` transaction does `rev++` in the `transaction` handler next to `history.record` (actions.js:288).
- `revLog` (module state in commands.js): ring buffer of the last 500 entries `{rev, before: tr.before, mapping: tr.mapping}` (ProseMirror docs share structure, so holding 500 old docs is cheap).
- Resolving a `PATH` sent with `ifRev = r`:
  1. `r === state.rev` → resolve against the current doc.
  2. `r < state.rev` and `revLog` has entry `r + 1` → `pos = posOfPath(entry.before, path)`; compose mappings `r+1 … state.rev` → `mapResult`; if `mapResult.deleted` → `stale`; else `pathOfPos(currentDoc, mapResult.pos)` is the path the command uses, and the result reports it.
  3. `r` older than the ring, `r > state.rev`, or from before the last mount (the log was cleared) → `stale{data: {rev: state.rev}}`.
- `(draftId, rev)` is the version key; `doc.get`, `doc.find`, `board.list` and every result carry it. Agents send `ifRev` with the rev their read returned; `doc.find` re-locates when `stale` comes back.

### 3.6 Events

Renderer emits, coalesced per type and debounced 150 ms: `draft.changed {draftId, rev}`, `draft.opened {draftId}`, `drafts.changed`, `settings.changed {keys}`, `selection.changed {kind: 'text'|'node'|'board', path?, ids?}`, `status.changed {loggedIn}`, `push.done {draftId}`, `agent.connected / agent.disconnected {name}`, `ui.changed {view, mode, busy}`. Sources: `subscribe` (store.js:44), `editor.on('transaction')`, `activeBoard.subscribe`, `canvasEditor.subscribe`. In-process: `commands.on(type, fn)`. Over the pipe: JSON-RPC notifications `event` to connections that sent `subscribe {events: [...]|'*'}`. Namespaces add their own (`plan.changed`).

### 3.7 Preconditions shared with the UI (`src/app/gates.mjs`)

The UI hides or disables a control when a requirement does not hold: no board is active, nothing is selected, the draft was never pushed, the board is a canvas and not a whiteboard. Each requirement is one named **gate** in the pure, import-free module `src/app/gates.mjs`. The UI and the command layer call the same gate; neither has its own copy of the check (user decision, 2026-10-06).

```js
// src/app/gates.mjs
export const GATES = {
  'draft.pushed': { subject: 'draft', test: (d) => d?.pushedAt != null,
    message: 'The draft is not marked as pushed', fix: 'Nothing to unpush; push.prepare pushes it' },
  'board.whiteboard': { subject: 'board', test: (b) => b?.kind === 'whiteboard',
    message: 'Only a whiteboard can do this, not a canvas', fix: 'Address a whiteboard block (board.list shows the kinds)' },
  // …
};
export const can = (id, subject, args, param) => GATES[id].test(subject, args, param);
```

- **Subjects.** A gate reads one subject: `draft` (`{id, threadUrl, pushedAt}`), `ui` (`{view, editor: boolean, mode}`), `board` (the `Board.getSnapshot()` shape, whiteboard.js:830-854: `{kind, mode, count, item, editing, canUndo, canRedo}`), `doc` (`{inTable, canUndo, canRedo}` from the editor), `plan` (the parsed plan) or `flow` (a library record, or the `flow` attr of the canvas at `path`; flowchart plan §7.2). The UI passes its current subject: the open draft, the active board's snapshot. The executor takes the subject from the command's arguments when the command addresses its target (`draftId`, `path`, `planId`; for a board node without a live `Board` it builds the same shape from the node's attrs), and from the live UI when the command acts on "the current" thing (`ui.*`, `tool.run`, `history.*`).
- **Declaring.** `needs` entries are a gate id or `{gate, if?, with?}`: `if(args)` limits the gate to some calls (`board.items.add` needs `board.whiteboard` only if an item is a `canvas`), `with` is the gate's parameter (the item types of `board.itemIs`).
- **Checking.** Executor step 5 (§3.3) runs every applicable gate and returns all failures at once (`precondition_failed`, §3.2). The agent changes its state or its target and retries.
- **The UI side.** tools.js entries declare `needs` instead of hand-written `when`: the predicates `inText`, `onBoard`, `onWhiteboard`, `itemIs` and `hasSelection` (tools.js:29-33) and the table entries' `isActive('table')` checks (tools.js:167-171) become gates, `when` is derived from `needs`, and `listTools` (tools.js:186-192) keeps filtering by it. An entry with `command` (§5.4) takes that command's `needs`, so the palette and the command cannot disagree. Disabled states read the same gates: Undo / Redo (`T.undo.disabled`, Toolbar.jsx:54-55), Push / Unpush (Sidebar.jsx:113-117). `active` (tools.js:44) is the pressed state of a toggle, not a gate. `tool.run` (§7) reports the failing gate of the entry it was asked to run.
- **What is not a gate.** A rule about the combination of arguments (a dependency cycle, a tag another column maps, an unmapped column) stays a namespace refusal (`refused {code}`); user activity in progress stays `busy`; policy stays `denied`.
- Namespaces add gates with the same shape; `GATES` merges them like `CATALOGUE` merges `defs` (Gantt plan §8.2: `plan.columnRoom`, `plan.otherColumn`; flowchart plan §7.2: `view.flows`, `node.canvas`, `flow.open`, `flow.synced`, `flow.unsynced`, `flow.present`).
- `gates.mjs` is seeded in roadmap Stage 1, before this layer, with the gates of today's controls and those of both sibling plans' controls; Phase 0 adds the rest.

## 4. Storage and IPC

### 4.1 Generic file family (`fileFamily`, main.js)

### 4.3 Data-model conventions (binding for every new system)

1. **Ids**: records in their own files use `crypto.randomUUID()` and are validated by `/^[a-f0-9-]{36}$/` before touching a path; sub-objects inside one node's attrs use 7-char base36 (`newId()` pattern), unique within that node. Never address stored data by index or title.
2. **Links by id**: `draftId`, normalised `threadUrl`, `ticketId`, `itemId`; prune dangling links with the `pruneMap` pattern (drafts-meta.js:24-27) on every save; never fail a load on them.
3. **Timestamps**: ms-epoch numbers `created`, `updated`, stamped by main on write (as `saveDraft`). Calendar dates are `YYYY-MM-DD` strings. No `Date` objects, no ISO timestamps in files.
4. **JSON-serialisable only**: plain objects/arrays/strings/finite numbers/booleans/null; `structuredClone`-safe. Data URLs allowed (history.js dedups them in node attrs automatically).
5. **Schema version**: every file family has top-level `version: N`. Node attrs carry `v` only once a breaking change exists. `parseX(json)` reads old shapes, fills defaults, drops invalid parts and **never throws** (`parseBoard` whiteboard.js:137 pattern). Migrations are pure `migrateX(file) → file` chains next to their `parseX` (e.g. `migratePlan` in `src/plan/plan-model.mjs`), run on load, written back on the next save; unreadable files are set aside as `.corrupt-<ts>` (main.js:85) and omitted from lists.
6. **Pure core**: data logic (reducers, validation, layout, date math, routing) in import-free `.mjs` tested by `node --test`; DOM/React only in views. A command's `plan` calls the same reducer the UI calls.
7. **Writes**: through main (`serialized` + `writeJsonAtomic`), deletes by rename into `.trash/`. The renderer never treats a cached file as truth across a `mountEditor`.
8. **Doc-embedded nodes**: `group: 'block', atom, selectable, draggable: false`, attrs `rendered: false`, `parseHTML div[data-<name>][data-json]` with `parse<X>`, inserted via `insertBoard(tr, topLevelPos(...))` (whiteboard.js:52-58), committed with one `setNodeMarkup` + `closeHistory` per gesture; export registered in `replaceWhiteboards` (doc-utils.mjs:39) and export.js:36, 42-52.
9. **Undo**: doc-embedded data rides TipTap history. Data outside the doc keeps its own in-memory undo (snapshot stack, 50) exposed as `<ns>.undo` / `<ns>.redo` (`undo: 'own'`); persistent own-history only when a real need appears (history.js `encode/rebuild` is the template). Settings writes have no undo: a command's result returns what it changed, and agents revert by writing the previous value (`settings.patch`) or with the inverse command (`tags.remove` returns the removed tag and its `draftIds`; `tags.add {id, …}` and `drafts.setTag` restore them).
10. **Every mutation is a command**: a feature ships its `define()` entries with `examples` and `needs` (§3.7), and a `tools.js` entry with `command:` when a human should reach it from Ctrl+Space. A control the UI gates gets its gate in `gates.mjs`, never an inline condition.
11. **Precise edits** (binding; user decisions, 2026-10-06): every command changes the smallest addressable unit — one entry, one item, one block, or one field set of one record (a bulk command applies that one change to the ids it names) — and never rewrites a whole document, board or list. Lists of records change through `<ns>.add` / `.update` / `.move` / `.remove`, each naming one id: tags, plan columns, estimate units, labels, saved views, holidays, and a ticket's dependencies, labels, checklist items and links. A patch merges the keys it names and keeps the rest (`board.items.update`, incl. a connector's `labels` and `heads` per slot; `plan.update`; a view's or chart's `options`). Why: a whole-list or whole-document write can drop entries the caller did not mean to touch, and it hides what changed from undo and the audit log. A field whose value is a set chosen as one setting is one field, not a list of records: a calendar's `workdays`, a view filter's `columns` / `labels` / `fields`, a connector's waypoints. `.add`, `.update` and `.move` are `write`; `.remove` of something the user made is `destructive`, of a link `write` (§5.2). The rule binds the command layer: the UI may group controls in one dialog, but every change it sends is one command. `batch` (§7) groups precise edits into one undo step and one ask; it is not a whole-document write.

### 4.4 Pipe protocol (main ↔ bridge)

- Path: Windows `\\.\pipe\daf-writer-<cyrb53(userData)>`; else `path.join(os.tmpdir(), 'daf-writer-<cyrb53(userData)>.sock')` (short: Unix socket paths are limited to ~104 bytes), `fs.chmod 0600` best effort.
- Framing: newline-delimited JSON-RPC 2.0, one parser `src/agent-wire.mjs` (pure, tested) shared by the server and the bridge (MCP stdio uses the same framing). Max message 64 MiB → `too_large` and the connection closes. Default timeout 60 s, `slow` 300 s.
- First message must be `hello {token, name, version, protocol: 1}` within 5 s → `{apiVersion, appVersion, draftId, rev, hidden}`; wrong token (compared with `crypto.timingSafeEqual` after length check) or no hello → socket closed. `source` becomes `agent:<name>`.
- Methods: `call {id, args, dryRun?, ifRev?, timeoutMs?}` → the §3.2 result; `subscribe {events}`; `capabilities` → `app.capabilities` (served from `capabilities.json` when the renderer is not ready yet); `tail {n, source?, draftId?}` → audit lines. Notification `$/cancelRequest {id}` → main forwards `agent.cancel {rid}` → the renderer aborts that call's `signal`. Notification `event {type, …}` from server to subscribers.
- Authentication is the token, rotated per server start; the pipe is only the transport (on Windows any local user can open a named pipe; `agent.json` is protected by the `%APPDATA%` ACL only). No TCP.

### 4.5 Main: `src/agent-server.js` and `api.agent`

- `start({userData, mainWin, getSettings})` / `stop()` (closes connections, removes `agent.json`). Started when `settings.agent.enabled` at launch or `--agent` is on argv **and** the setting is on; `setSettings` (main.js:91-98) detects a change of `agent.enabled` and starts/stops live; disabling drops connections.
- `second-instance` (main.js:489-494) receives the second launch's argv: with `--agent` → start the server if enabled (and do not show the window when `--hidden` is also present); if disabled → `mainWin.webContents.send('agent.event', {type: 'agent.blocked'})` (toast "An agent tried to connect. Allow local AI agents in Settings."). Without `--agent` the handler behaves as today.
- Forwarding: `call` → `mainWin.webContents.send('agent.call', {rid, req})`; `ipcMain.on('agent.reply', (e, rid, res))` and `ipcMain.on('agent.event', (e, ev))` check `e.sender === mainWin.webContents` (same rule as `handle`). Calls queue until the renderer sent `agent.ready`; a destroyed window rejects every pending call with `failed`. Main never interprets command semantics; it validates the envelope (`isPlainObject`, id pattern, size).
- `--hidden`: `createMainWindow({hidden: true})` → `show: false` stays, the `ready-to-show → show()` is skipped, `webPreferences.backgroundThrottling: false` (rAF and timers must run for `board.render` / `export.preview`, whose rasterizer measures DOM and waits frames). Idle shutdown: started hidden and never shown → `app.quit()` `idleQuitMinutes` after the last connection closes. The renderer learns `hidden` from `agent.call` payloads (`hidden: true`) and from `app.info`.
- Preload (`preload.js`, +6 lines): `api.agent = { onCall(fn), reply(rid, res), event(ev), ready(capabilities), control(action) }` — `onCall` wraps `ipcRenderer.on('agent.call')`, `reply`/`event`/`ready` are `ipcRenderer.send`, `control` is `ipcRenderer.invoke('agent.control', action)` (sender-checked `handle`) with `action ∈ {type: 'disconnect', name} | {type: 'status'}` → `{connections: [{name, since}], hidden, enabled}`. The renderer never sees the token or the pipe path.

### 4.6 Bridge `bin/daf-agent.js` (plain Node ≥ 20, stdlib only)

- `daf-agent` (no args) = MCP server on stdio. `initialize` → echo the client's `protocolVersion` when it is one the bridge implements, else the newest it implements (one constant `MCP_VERSIONS`; verify the current list at implementation time against modelcontextprotocol.io — at planning time `2025-06-18` is the newest we know), capabilities `{tools: {}}`; `notifications/initialized`; `ping`; `tools/list`; `tools/call`. Results: text content with the JSON result; a result field `png` (base64) becomes `image` content (`board.render`, `plan.render`); `ok: false` → `isError: true` with the error JSON as text.
- **Curated tools** (≈ 22, so hosts do not drown): `app_info, ui_state, drafts_list, drafts_get, drafts_create, drafts_open, drafts_set_tag, doc_get, doc_find, doc_insert, doc_replace, doc_delete, doc_format, board_list, board_get, board_insert, board_items_add, board_items_update, board_render, threads_list, tags_list, push_prepare`, plus two generic ones: `daf_capabilities` (the full catalogue) and `daf_call {id, args, dryRun?, ifRev?}` (any command). Namespaces can add to the curated list with a `mcp: true` flag on `define`. Since 2026-10-06 (§13.2 Tool calls) the bridge may expose `commands_index` and `commands_describe` (§7) in place of `daf_capabilities`, so a host starts from a small list and fetches schemas when it needs them; the host form of the schemas keeps the ` Needs:` text (SPEC §8 Tool schemas).
- `inputSchema` rewriting for hosts: dereference `$ref` into the schema, `oneOf` → `anyOf`, `type: ['string','null']` → `anyOf: [{type:'string'},{type:'null'}]`, drop `default`/`examples`. `tools/list` reads `userData/capabilities.json` when the app is not running (no Electron launch for a listing).
- CLI: `daf-agent call <id> [json] [--dry-run] [--if-rev N]`, `daf-agent list`, `daf-agent tail [n]`, `daf-agent status`; prints JSON, exit 1 on `ok: false`.

A running instance receives that argv through `second-instance` (§4.5): with agents enabled the server starts; otherwise the bridge fails with "DAF Writer is running without agents enabled: Settings → Allow local AI agents".

### 5.2 Approval policy

| risk | `ui` / `palette` | `smoke` | `agent:*` (per-connection policy `{write: true, destructive: 'ask', approval: 'ask'}`) |
|---|---|---|---|
| read | run | run | run |

**What counts as destructive** (binding for every namespace): a command that can remove something the user made — a draft, folder, thread, tag, document block, board item, plan, ticket, plan column, estimate unit, label, saved view, holiday, or a ticket's checklist item or link. ## 6. Insertion into drafts and export

### 6.1 `doc.insert` / `doc.replace` content forms

`content` is exactly one of:
- `json`: a TipTap node or array of block nodes → `schema.nodeFromJSON` each (`check()`; failure → `invalid_args{path}`).
- `html`: → `generateJSON(html, editor.extensionManager.extensions)` (renderer has a DOM). The schema's accept/reject rules (extensions.js:20-22, 44, 78, 112, 145) drop forum-illegal styling by construction. `<img>` has no node: images in HTML are dropped and reported in `result.dropped: ['img']`; use `images`.
- `markdown`: → TipTap JSON through `@tiptap/markdown` (§8). Fenced code, tables, headings, lists, quotes, links, bold/italic/strike/code map to the schema; unknown constructs degrade to paragraphs; `![](data:…)` images are dropped and reported like `<img>`.
- `images: [{dataUrl, w?, h?}]` → one `canvas` node per image, artboard = natural size (decoded in the renderer, ≤ 8000 px per side), `dw = min(w, forumWidth)` (the `addImages` pattern, whiteboard.js:473-493, without the paste plumbing). `maxLength` of `dataUrl` 20 MB; total request ≤ 64 MiB.

Placement: `at ∈ PATH | 'start' | 'end' | 'cursor'`, `position ∈ 'before' | 'after'` (default `after`) relative to the block at `at`; `'cursor'` = `afterNodeSel` of the current selection (actions.js:162-165) without moving it. Board nodes (`whiteboard`, `canvas`, `planChart`; a flowchart is a `canvas`) in the content are forced to the top level (`topLevelPos`): when `at` is nested they go after its top-level ancestor; `result.paths` lists where every inserted block landed. `doc.replace {path, content}` replaces the block at `path`; a board node at `path` is refused (`denied{reason: 'policy', hint}`) because replacing it removes its items: board contents change through `board.*` / `flow.*` / `plan.chart.set`, and swapping a board is `batch [doc.delete, doc.insert]`, which asks once (§5.1). `doc.delete {paths}` (destructive, §5.2) deletes in descending document order in one transaction. All three: one transaction, `undo: 'doc'`.

### 6.2 `doc.format`

`{path, from?, to?, marks?, block?, presetId?}`: `from/to` are block-local text offsets as `doc.find` returns (default: the whole block); `marks` keys: `bold, italic, underline, strike, sub, sup, code` (boolean), `fontSize` (80|90|100|125|150|175|200|null), `textColor` (TEXT_COLORS key|null), `highlight` (HIGHLIGHTS key|null), `fontFamily` (FONTS css|null), `link` (href|null); `block`: `{type: 'paragraph'|'heading', level?: 1..6, align?: 'left'|'center'|'right'|'justify'}`; `presetId` applies `applyPreset` (extensions.js:248-260) semantics. One chain: `setTextSelection(range)` → marks/block → `setTextSelection(previous selection mapped through the transaction)` so the user's selection is untouched; dispatched without focus.

### 6.3 Boards (`board.*`)

- `board.list` / `board.get` read node attrs from the doc (`board.get` replaces data URLs by `{$img: {len, hash}}` unless `images: true`; `itemPath` reads a canvas item's inner board).
- `board.insert {kind: 'whiteboard'|'canvas', at, attrs?}`: attrs through `parseBoard` / `parseCanvas` (whiteboard.js:137, canvas.js:43-52) by stringifying them (the parsers take JSON text), then `insertWhiteboard` / `insertCanvas` semantics via `insertBoard`.
- `board.items.add {path, itemPath?, items: ITEM[]}`: items get fresh ids (`newId` pattern) unless the given id is unused on that board (connector ends that name an item of the same call follow its final id: `cloneItems`, flowchart plan §6), then `validItem` + `cleanItem`. Then:
  - **whiteboard node** (always has a live `Board`: `editor.view.nodeDOM(pos).wbView`, as WhiteboardPaste does at whiteboard.js:474/531): `for (i of items) { board.items.push(i); board.clampItem(i); } board.commit(true)` → one `host.commit` → one `setNodeMarkup` (whiteboard.js:1917-1923) with smart height, clamping and text measurement for free. `busy` rules of §3.3 apply.
  - **canvas node** without a session (no live `Board`): measure text heights by appending `itemElement(item)` to an offscreen hidden div (the `Board.itemHeight` trick, whiteboard.js:1013-1023, without a Board), compute `smartArtboard(frame, {w, h}, contentBox)` (whiteboard.js:117-124, pure, tested), shift items by `dx/dy`, keep `dw` by the `nodeTarget` ratio rule (canvas.js:294), one `setNodeMarkup` + `closeHistory`.
  - **canvas item inside a whiteboard** (`itemPath`): same measurement + `smartArtboard` on the item's `aw/ah/frame/items`, displayed size by the `itemTarget` ratio rule (canvas.js:321-334), then the parent whiteboard's `board.commit(true)`.
  - **Connector geometry** (flowchart plan §3.4): the whiteboard route gets it from `board.commit(true)`, which resolves connectors once that plan's Phase 0 lands; the two routes without a live `Board` first run `settle(attrs)` = `resolveConnectors(items)` from `src/flow/route.mjs`, before measuring, so the stored `x y w h d tips lps` are never stale. Results carry `warnings` for connector ends repaired or dropped (flowchart plan §3.3).
  - No refactor of whiteboard.js or canvas.js is needed; the two engineers' files are only *imported*.
- `board.items.update {path, itemPath?, id, patch}`, `board.items.remove {path, ids}`, `board.items.arrange {path, ids, where}`: same three routes; `update` merges top-level keys, and `labels` / `heads` per slot (`{labels: {mid: {html: 'yes'}}}` changes the middle label only, `{labels: {end: null}}` removes that slot; precise edits, §4.3 #11), then revalidates the merged item; `remove` is destructive (§5.2), and connectors bound to removed items stay, their ends freed at their tips.
- **Library flowcharts** (flowchart plan §3.8–§3.9, §7.1): `board.*` also accept `{flowId}` in place of `{path}` (needs `flow.present`); the subject is the record's board, writes take the canvas route without a live `Board` above and end in `ctx.flows.save` (a new `rev`, one entry on the record's own undo stack, `undo: 'own'`). ## 10. Risks and mitigations

- **Lost update between an agent write and a live gesture**: `Board.setAttrs` defers while `gesture` / `editingId` (whiteboard.js:841-845) and the gesture's commit would overwrite. Mitigation: `busy` on the *target* board only (§3.3 #7); agents retry on `busy`; agent writes never end the user's text edit.
- **Agent paths going stale while the user types**: mitigated by `ifRev` + the mapping log (§3.4). Residual: a mapped position inside a block the user is retyping still edits "the right block" but may surprise; `doc.replace` results report the resolved path so the agent can show it. Upgrade path if ever needed: block id attrs stripped at export.
- **Undo grouping drift**: a command dispatching two transactions makes two steps. `undoSteps` in every result + the smoke `expect` catch it in CI-like runs; `batch` is the sanctioned way to group.
- **UI and command checks drifting apart**: one `gates.mjs` used by both; tools.js derives `when` from `needs`; the contract test checks every gate id; an inline condition that hides or disables a control is a review finding (§4.3 #10).
- **Hidden-window rendering**: Chromium throttles hidden renderers; `backgroundThrottling: false` keeps rAF/timers running and layout works unshown, but html-to-image in a never-shown window is unverified. Phase 3 exit test; fallback `showInactive()` + `setPosition(-32000, -32000)` + `setSkipTaskbar(true)`; last resort `board.render`/`export.preview` → `failed{code: 'hidden'}` and a documented limitation.
- **Hidden instance lifecycle**: idle quit (10 min after the last connection, `app.quit` command for explicit teardown); a user launching the app shows the hidden instance (`second-instance`) and sees the agent indicator; `lastDraftId` never changes from agent sources.
- **Confirm fatigue / dialog collision**: agent asks are queued, non-modal and never share the user's `confirm` slot; destructive commands ask on every call (user decision, no session approval), and an agent that deletes several things at once sends one `batch`, which asks once and lists every destructive step; `write` commands never ask (trash and undo make them safe), and rewording or shortening text inside a block is `doc.replace` (write), so only whole-block deletes (`doc.delete`) ask (user decision); lists change per entry (§4.3 #11), so adding a tag, column, unit, label or view never asks.
- **Concurrency on settings**: the executor serializes external calls and re-reads `state.settings` inside the section; main merges per top-level key, so a simultaneous human click on a *different* key never loses; the same key is last-writer-wins within one click — accepted.
- **MCP protocol drift (no SDK)**: one `MCP_VERSIONS` constant in the bridge; the bridge is isolated, swapping to the SDK touches no app code. Host schema limits handled by the rewriting rules (§4.6).
- **Windows pipe ACL / Unix socket path length**: token is the authentication (rotated per start, `timingSafeEqual`); socket in `os.tmpdir()`.
- **Big payloads**: 64 MiB per message, 20 MB per image, `argsDigest` in audit, `board.get`/`drafts.get` strip images unless asked.
- **Engineers mid-change in whiteboard.js / canvas.js / history.js**: this layer imports from them (`parseBoard`, `smartArtboard`, `itemElement`, `rasterizeWhiteboard`, `withoutScroll`, `SHAPES/FILLS`, `canvasEditor`, `activeBoard`) and edits none of them; the one touched shared file is actions.js (§5.5), coordinated as Phase 0's last commit; `history.js` is untouched (hash copied).
- **`@tiptap/markdown` unavailable or DOM-bound in Node**: fallback named in §8; Markdown tests move to the smoke script if the parser needs a DOM.
- **Security regression by convenience**: default off, token file, renderer blind to token and pipe, no TCP, `doc.command` allowlist, `forum.*` surface fixed at status/login/open/push-prepare, pickers denied for agents, `headless: false` denied when hidden.
- **Smoke persistence**: the agent script writes into `--data-dir` (default `.smoke-data/`, gitignored); `__smoke()` keeps `state.smoke = true` and never persists.

### 13.1 How it calls the app
- An in-process client in the renderer (`src/app/assistant.js`) turns the model's tool calls into `invoke({id, args, source: 'agent:assistant', ifRev})` (§3.3) and hands the §3.2 result back to the model. No MCP, no pipe, no token. It gets the same schema validation, gates (§3.7), approval cards (§5.1), audit and events as every agent, under the `agent:*` policy (§5.2): writes run, destructive and approval steps ask on every call.
- The model's tools are `app.capabilities {available: true}` (§7) with the §4.6 schema rewriting, moved into a pure module shared with the bridge; since 2026-10-06 a small subset in the model form, and the model adds more with `commands.describe` (§13.2 Tool calls). llama.cpp does not enforce argument schemas (§13.2), so the registry's validation is the only check. A `precondition_failed` result names the gate and its fix, so the model fixes its state and retries instead of guessing.
- Inference runs outside the sandboxed renderer: main starts `llama-server` as a child process on `127.0.0.1` (§13.2), or uses one the user points to, and relays text, audio and images over IPC (`api.assistant`, sender-checked like `api.agent`, §4.5). The renderer opens no network connection, so the CSP (index.html:5) stays unchanged; it also rules out WebAssembly inference in the renderer.

It does not fit with headroom, and without it only on a card with ≥ 7.4 free and nothing else on the GPU. So the first degrade step is the one that frees the most for the least cost: with the projector on the CPU the total is 5.8–6.0 without headroom, 6.8–7.5 with it (fits a card leaving 7.6; on a 7.2 card step 2 is needed as well). On NVIDIA, Windows' sysmem fallback may page the overflow to system RAM instead of failing the load, so no step runs and replies crawl (Games alongside, below: "Prefer No Sysmem Fallback"). When the server fails to load or exits out of memory, main applies the next step, restarts, and keeps the step in `settings.assistant.step` (a stored step above 3, e.g. from the 4B's old ladder, runs as 3):
Default since 2026-10-06 (user decision): `--no-mmproj-offload` on every launch under 10,000 MiB of GPU memory or when it is unknown (Gemma 4 12B excepted, §11 Q22: its projector is 0.16 GiB, so it stays on the GPU; from 10,000 MiB, reliability plan wave 2, the projector runs on the GPU too), so the projector and image encoder run on the CPU (≈ 1.1–1.4 freed; text speed unchanged, image encoding slower). The remaining steps:
1. `--cache-type-k q8_0 --cache-type-v q8_0`: halves the KV cache (≈ 0.23 freed); never `q4_0`.
2. `-ngl 24`: the first 9 of 32 layers on the CPU (llama.cpp counts the output layer among the 24; ≈ 1.2 freed with their KV share; slowest).

Dropped with the 9B: the smaller-context step (16 K is the user's choice and 8 K would not hold a tool turn plus history); the smaller-picture step stays a client setting (checklist item 2); a smaller file (`IQ4_XS` 5.17 GB, `Q3_K_M` 4.67 GB at the same commit) or the 4B tier is a user choice, not an automatic step.

The Gemma tier keeps its own steps (Runner-up below).

**Images**
- The renderer rasterizes (`doc.render`, `board.render`, §13.3), the PNG goes to main as a data URI, and main sends it as an `image_url` part. A `png` inside a command result reaches the model as an image part of the next message; the rest of the result is the `role: 'tool'` message.
- llama.cpp resizes each image by Qwen's own rules (dynamic resolution, no trained token budgets), so the client sends each picture at a long side ≤ 1280 px, keeping its aspect ratio; the tokens per picture are logged on the first runs (checklist item 2). The Gemma tier keeps its 48-px cell sizing (Runner-up below).
- Crops for detail: a tall draft goes as the blocks or the region the question is about (`doc.render {paths | region}`), each within the cap, never as one shrunken page; small text means a tighter region, not a larger picture.
- At most 4 pictures in the 16 K context (planned; 8 at 32 K before §11 Q19); when the context fills, older pictures leave the history first. Pictures are cached per `(draftId, rev, region, size)` (§13.5).

**Tool calls**
- `tools` (user decision 2026-10-06, §11 Q18) = core ∪ the current view's set ∪ the tools the model described, in the model form (SPEC §8 Tool schemas: description = the title, no limits, patterns or `additionalProperties`, `ITEM` as one flat object); the core and view tools only while their gates hold (`app.capabilities {available: true}`); `parallel_tool_calls: false`; thinking off, except maths requests that think with `calc.eval` (§13.16). Measured over the real catalogue at 3.5 characters per token: the old curated list was 25,462 characters (≈ 7.3 K tokens), 13,976 of them `board_items_add`; now core + editor 5,267 (≈ 1.5 K), core + board 5,856 (≈ 1.7 K), core + no draft 3,293 (≈ 0.9 K), core + Plans 2,285 (≈ 0.65 K), core alone 1,614 (≈ 0.46 K); `board_items_add` 2,369; the whole catalogue in the model form 22,535.
  - Core (always): `ui.state, drafts.list, drafts.open, batch, commands.index, commands.describe`.
  - View sets (`src/app/commands/tool-sets.mjs`; `viewOf`: the page when it is not the editor; no open draft → none; caret in text → editor; a whiteboard active or a canvas being edited → board): editor `doc.get, doc.find, doc.selection, doc.insert, doc.replace, doc.delete, doc.format, board.list`; board `board.list, board.get, board.items.add, board.items.update, board.items.remove, ui.select`; none `drafts.create, drafts.get, drafts.setTag, drafts.delete, threads.list, tags.list, folders.list`; plan `drafts.get, drafts.setTag, tags.list` (`plan.*` joins when it registers); flows: the core only (`flow.*` joins when it registers; nothing addresses a library flowchart yet).
  - Never offered, not even through describe: `history.undo`, `history.redo` (the model must not undo the user's own typing; each step line has Undo), and `tool.run` (its palette Undo / Redo entries would do the same). `board.render` is in no set (its PNG would reach a text-only model as base64) but can be described.
  - Budgets (test/tools-schema.test.mjs): core + any one view set ≤ 7,000 characters; one model-form tool ≤ 2,600; property descriptions in the sets ≤ 80 (`ITEM_BRIEF`'s field lists excepted); described tools ≤ 8,000 per session, oldest dropped first. Worst request ≤ 15,000 characters ≈ 4.3 K tokens.
  - Discovery and planning: `commands_index {category | view | q}` lists more tools; `commands_describe {names}` adds up to 6 to the next request (the chat template re-renders the tool block, a prompt re-pass of 1 to 2 K tokens) and the model gets `{added, risk}` back, not the schemas a second time. Described tools stay while the view key stays and are dropped when it changes (a board tool is dead weight on the Plans page). A call to a tool that is not offered answers `unknown_command` "<name> is not one of your tools (commands_describe adds it)". The tool rules tell the model: for several changes, add the tools it needs, read the paths, then run one `batch` (index, describe, read and batch are 4 of the 8 calls); the batch shows one card for its destructive steps and makes one undo step.
- llama.cpp's tool-call parser for the model's chat template (`--jinja`) parses the call but does not enforce the argument schema. The registry validates (`invalid_args` with `path` and `expected`), checks gates and asks for approval as for every agent (§3.3), and the typed result, error or not, goes back as the `role: 'tool'` message, so the model corrects its call. The same call failing twice stops the turn and shows the error. A tool call left as text in `content` counts as a parse failure and is re-asked once.
- Single-step commands: prompts ask for one command per turn and long chains are not attempted, because Qwen3.5-4B's τ²-bench 79.9 is vendor-reported and no independent number exists; a change of several steps is one `batch` call (§7). The 10-step chain test (checklist item 12) shows whether longer chains can be allowed.
- Generative payloads (a flowchart graph for `flow.insert`, plan edits) come from a separate request with `response_format: {type: 'json_schema', schema}`: the grammar rules out malformed JSON, and the client passes the payload to the command, which validates it again.

**Integration in main** (`src/assistant-runtime.js`, CommonJS)
- **Install**, only when the user starts it: Settings → Assistant → Install shows the licences, the backend found, the model choice and the download size. Files download as `.part` with progress into `userData/assistant/llama-<build>/` and `userData/assistant/models/`, from URLs pinned to a Hugging Face commit (Unsloth re-uploads files when chat templates change; for Qwen3.5, a commit after its 2026-03-05 tool-calling template fix) and checked against SHA-256 values pinned in the app; a mismatch deletes the file and fails the install. "Use existing files" takes the user's own `llama-server.exe` and model paths, unchecked.
- **Lifecycle**: warmed in the background at app start when installed and enabled, slept and unloaded when idle, and restarted by the first request after an unload (Warm-up and idle, below; user decision 2026-10-06, §11 Q13; it holds ≈ 6–7.4 GB of VRAM while loaded with the 9B, VRAM budget above). Free port, new key, `spawn(exe, args, {windowsHide: true})`; poll `GET /health` until 200 (503 while loading; after 120 s the stderr tail is shown). On the first run main logs `CUDA0 model buffer size`, `CPU_Mapped model buffer size`, `KV self size` and `compute buffer size` to confirm the budget. The PID goes into `userData/assistant/server.json`: killed on `before-quit`, and a stale one left by a crash is killed on the next start after checking its image name. An unexpected exit sets the status to `stopped`; the next request restarts the server. `/health` serves only the first load: after it, the server stays 200 while asleep and while reloading, so the status comes from `/props` (Warm-up and idle).
- **IPC** `api.assistant` (preload, sender-checked like `api.agent`, §4.5): `install(opts)`, `start()`, `stop()`, `status()`, `chat({rid, messages, tools? | response_format?, think?})` streamed as `assistant.event {rid, type: 'delta' | 'reasoning' | 'tool_call' | 'done' | 'error'}` through `webContents.send`, `transcribe({wav}) → {text}`, `cancel(rid)`. The renderer never sees the port or the key.
- **Streaming and cancel**: main calls `/v1/chat/completions` with `fetch`, `stream: true` and an `AbortController`. Stop (§13.4) aborts the request, the socket closes, and llama-server stops generating and frees the slot. Main never sends `X-Conversation-Id`, which turns on llama-server's replay buffer.

API keys never go into settings.json: main stores them encrypted with `safeStorage` in `userData/assistant/keys.json`, and settings hold only `hasKey` flags (§13.15).

**Warm-up and idle** (user decision 2026-10-06, §11 Q13: when installed, both models warm in the background at app start; idle cost as low as each server allows)
- **Dictation first**: the whisper warm-up is being implemented now (SPEC §7h) and the assistant follows the same rules. 2 s after `ready-to-show` (main.js), when the dictation is installed and `settings.dictation.warmAtStart` (default true), main runs the existing warm path (`serverUrl`, as the `dictation.warm` handler), errors swallowed. Measured 2026-10-06 with small: ready in ≈ 0.65 s, ≈ 0.58 GB working set, 1.1–1.2 GB committed, ≈ 0 CPU at idle, no VRAM. `whisper-server` has no idle, sleep or unload flag, so the only lever is stopping it; it stays up (user decision 2026-10-06, §11 Q16). The mic hover, push-to-talk and the crash restart warm it as today.
- **Start**: 10 s after `ready-to-show`, after whisper, so the window paints first and the two loads do not share the disk; only when the assistant is installed, `enabled` and `warmAtStart` (default true), and not on battery (`powerMonitor.isOnBatteryPower()`; user decision 2026-10-06, §11 Q15). Same spawn as Lifecycle above.
- **Priority** (both servers): `os.setPriority(pid, os.constants.priority.PRIORITY_BELOW_NORMAL)` right after `spawn`, in a try/catch. Node maps it to `BELOW_NORMAL_PRIORITY_CLASS` (thread base priority 6 instead of 8), so a game at normal priority wins the CPU and transcription slows only under contention. Set on the child, not on Electron, whose children would inherit it. Not `PRIORITY_LOW` (the idle class; a game could starve it). It changes CPU scheduling only: I/O and memory priority need `PROCESS_MODE_BACKGROUND_BEGIN`, which works only on the calling process, and GPU work is unaffected.
- **Tier 1, sleep after 10 min** (`--sleep-idle-seconds`, launch table): llama-server's own idle sleep (PR #18228) frees the model, the KV cache and the projector from VRAM and RAM and keeps the process. Every request except `GET /health`, `/props`, `/models` and `/metrics` resets the timer, and one that arrives while asleep waits until the model is reloaded (≈ 2–4 s with the file in the page cache, estimate). The CUDA context stays: ≈ 0.15–0.6 GB in reports (issue #19379; PR #25271, still open, would release it).
- **Status**: while the chat panel is open or a request waits, main polls `GET /props` (every 1 s, planned), which neither wakes the server nor resets its timer, and the chat panel shows "Waking…" while `is_sleeping` is true (it turns false only when the reload has finished).
- **Tier 2, unload after 30 min** (`idleUnloadMinutes`): main kills the process, as on `before-quit`. Only killing frees all VRAM: the PRs that would exit on sleep (#25243, #27307) were closed unmerged. The next request or a re-warm trigger restarts it (≈ 3–6 s with the file in the page cache, estimate). If PR #25271 lands in a later pin, Tier 2 can move later.
- **Power** (`powerMonitor` events in main): `on-battery` → kill, no re-warm until `on-ac` (user decision 2026-10-06, §11 Q15: a laptop safeguard; the user expects most users to be on desktops); `suspend` → kill (a CUDA context surviving sleep is unverified; a restart is safe); `lock-screen` → kill after 5 min locked; `on-ac`, `unlock-screen` and `resume` → re-warm after 10 s when `warmAtStart` is on (after `resume` only if the window has focus, else on the next request). Whisper stays up through all of them: no GPU, ≈ 0 idle CPU, and its crash restart covers a process lost in sleep. On battery nothing loads the assistant by itself (planned, not the user's words): not the start warm-up, a power event (`unlock-screen`, `resume`) or the grammar check's model pass (§13.14); the chat panel still starts it when the user opens it, holds its mic button or sends a message, and the idle tiers unload it as on mains.
- **Re-warm triggers**: app start; opening the chat panel (§13.4), which sends `POST /tokenize {"content": "hi"}` to wake a sleeping server without running a task (or restarts a killed one), so the reload overlaps the user's typing; holding the panel's mic button (it warms whisper too); the first real request, including the grammar check's model pass when it is on (§13.14, §11 Q11; not on battery); the power events above. Push-to-talk dictation into a draft does not warm the assistant.
- **Games alongside**: Electron cannot detect a game starting. When a game needs VRAM a loaded server holds, Windows (WDDM) pages the server's allocations out to system RAM: nothing crashes, the game gets the memory after paging, and the next reply is slow until the pages return (magnitude unmeasured). The two tiers are the mitigation. Settings → Assistant says: "While the assistant is loaded it holds about 6 to 7 GB of GPU memory. It sleeps after 10 min and unloads after 30 min." On NVIDIA it suggests NVIDIA Control Panel → Manage 3D Settings → "CUDA - Sysmem Fallback Policy" → "Prefer No Sysmem Fallback" for `llama-server.exe`, so a reload without room fails fast and the degrade steps run instead of crawling in shared memory (setting name from a secondary source; its per-program scope, driver version and effect unverified).
- **Idle power**: a loaded idle server cost no measurable power on an already-awake RTX 4070 (research pass, Vulkan build; CUDA on a GPU that would otherwise drop to P8 is unmeasured). On AMD a sleeping server keeps clocks and power high (PR #25243, issue #19318), so Tier 2 matters more there.
- **Settings**: `settings.assistant.warmAtStart`, `sleepMinutes`, `idleUnloadMinutes` (Settings above); `settings.dictation.warmAtStart: true` (SPEC §7h).

### 13.3 Perception commands it needs (all `read`)
- **Document outline with block ids**: `doc.get {format: 'outline'}` (§7) with a stable `id` per block. The ids are the §12 block-id item; they survive remounts and long sessions and are stripped at export.
- **Pictures for vision**: `doc.render {paths? | region?: {x, y, w, h}, scale?: 0.25..2}` → `{png, width, height, blocks: [{path, id, y, h}]}`: the draft as the forum will show it (forum width, page theme, editor-only chrome filtered out), whole, some blocks, or a region in post px. `board.render` and `plan.render` picture one board or chart. The client sizes each picture for the model as §13.2 Images describes.
- **Geometry for placing annotations**: `doc.layout {paths?}` → `[{path, id, type, x, y, w, h}]` in post px (origin: top-left of the draft content at 100 % zoom). A board node adds `board: {scale, items: [{id, x, y, w, h, rot?}]}`, `scale` = post px per board px, so a point the model picks on a picture maps to board px for `board.items.add` or `flow.connect`. Images are canvases, so an annotation on a picture is items added to its canvas: a precise edit, one undo step.
- **State**: `ui.state` (§7: `view`, `mode`, `tool`, `selection`, `busy`, `gates`); the events `selection.changed`, `draft.changed`, `ui.changed` (§3.6) push changes, so the client does not poll.
- **Available commands**: `app.capabilities {available: true}`, with schemas and the gates each command needs; `commands.index` (the categories, or the tools of a category, view or word search) and `commands.describe` (model-form schemas of up to 6 tools) for a model that starts with a small list (§7, §13.2 Tool calls).
- **Boards and the screen**: `board.read`, `board.query`, `view.read` and `view.render` (§13.8–§13.10) give compact records of what is on a board and on screen, with ids the model acts on.

### 13.5 Latency and streaming
- Commands take milliseconds. Renders take longer (html-to-image; to be measured), and so do image encoding and the prompt pass on an 8 GB card (§13.2 checklist). The client reads the outline first, asks for a picture only when it needs to see, within the picture cap or as a region (§13.2 Images), and caches pictures per `(draftId, rev, region, size)`.
- Model output streams into the transcript. Tool calls run as they arrive through the one queue (§3.3 step 1); the user's typing is never blocked, and `busy` (§3.3 step 7) protects the board the user is drawing on.
- Context budget (built 2026-10-06, SPEC §7i Context): every request asks `stream_options.include_usage`; the stream's usage chunk (else the last chunk's `timings`) and `/props` `n_ctx` feed the context ring and the 80 % compaction (§13.4). The pinned b11433 sends the finish chunk, then the usage chunk with `choices: []`, with `timings` on the last chunk (read from its `server-task.cpp`); the client handles both sources, so `done` now comes at `[DONE]`.
- No zombie processes (user rule; process audit 2026-10-06 with stub `llama-server.exe` / `whisper-server.exe`): both servers and Electron's helper processes end on a normal quit (`will-quit` kills the servers), on `app.exit` and a crash of main (`process.abort`) and on a forced kill of the main process, because both are spawned without `detached` into Node's Windows job object (kill on close). No change was needed.

### 13.8 Canvas reading: `board.read`, `board.query` (user request, 2026-10-06)

The model reads a board as compact records, not as a picture or raw attrs (`board.get` stays the full read).
- `boardRef` = `{path, itemPath?}` or `{flowId}` (the §6.3 addresses). Both commands are `read` and need what `board.get` needs: `doc.open` + `node.board`, or `flow.present`.
- `board.read {boardRef, cursor?, maxTokens?: 200..8000 = 2000}` → `{rev, units, summary?, items, nextCursor?}`.
  - Item record (empty keys omitted): `{id, type, kind?, text?, x, y, w, h, rot?, z, from?, to?, container?, group?}`. `type` = the `ITEM` type (`shape`, `text`, `canvas`, `connector`, `pen`, …); `kind` = the shape (`rect`, `diamond`, …); `text` = the plain text of its label, first 120 chars (a connector's labels as `start | mid | end`); `x y w h` = the unrotated box in post px (`units: 'post'`, origin as `doc.layout`, §13.3; a library flowchart has no place in a post, so board px, `units: 'board'`); `rot` in degrees; `z` = paint order; `from` / `to` = a connector's end item ids; `container` = the canvas item it sits in (`itemPath`); `group` once groups exist (flowchart Phase 5).
  - First page only: `summary = {count, byType: {shape: 12, …}, bounds: {x, y, w, h}, containers: [{id, count}], groups?}`.
  - Order: reading order (rows top to bottom, then left to right, by box top-left); connectors follow the items they join, so a page holds a region and its links.
  - Pages: records are added while the page's JSON stays under `maxTokens` (estimated as characters / 3, conservative for both tokenizers; checklist item 1 calibrates it). `nextCursor` is opaque `{hash, offset}`; `hash` = cyrb53 of that board's items (`digest.mjs`, §4.2), so typing elsewhere in the draft does not invalidate it. A changed board → `stale`, and the model starts again at page one.
- `board.query {boardRef, near?: {x, y, r}, type?, text?, limit?: 1..50 = 20}` → `{rev, units, items}`: the same records, filtered by `type`, by a case-insensitive substring of `text` and by distance of the item's centre from `(x, y)` (same units), nearest first.
- Pure helpers in `src/app/assistant/scene.mjs`: `sceneRecords(board, {scale, origin})`, `pageRecords(records, maxTokens, cursor)`, `queryRecords`, `anchorRect` (§13.10); tested by `node --test`.

### 13.9 Viewport: `view.read`

- `view.read {buffer?: 0..1 = 0.25, maxTokens?: 200..8000 = 1500}` (read, `headless: false`) → `{page, units, rect, zoom, mode, tool, selection, boards, blocks, items, truncated?}`.
  - `page` = `'editor' | 'plan' | 'flows'` (`state.view.type`, SPEC §7g). `rect` = the visible part of the page's viewport (`viewportRect()`, `src/app/viewport.js`) in post px in the editor (`units: 'post'`), in board px while a canvas is edited or in the library editor (`units: 'board'`). `zoom`, `mode`, `tool` and `selection` as `ui.state` (§7).
  - `boards` = `[{boardRef, kind, vis}]`; `blocks` = `[{path, id?, type, text, vis}]` (`text` = 60 chars); `items` = `[{n, board, vis, …the board.read record}]` (`board` = index into `boards`).
  - `vis`: `inView` (inside `rect`), `partial` (crosses its edge), `nearView` (outside `rect`, inside `rect` grown by `buffer` × its width and height on each side). Nothing beyond the buffer is listed. Over `maxTokens`, `nearView` entries go first, then `partial`, and `truncated: true`.
  - `n` = the mark number §13.10 draws, the same for the same `(rev, rect)`.
- The plan page reports `page`, `selection` and `rect: null` until the Gantt plan adds its records (its Phase 4).

### 13.10 Screenshots with Set-of-Marks: `view.render`

- `view.render {region?: {x, y, w, h}, marks?: true, maxSide?: 320..2048 = 1280}` (read, `headless: false`, `slow`) → `{png, width, height, units, rect, marks: [{n, id, x, y}]}`; `region` in `view.read`'s units.
  - Inside the viewport, main captures what the user sees with `webContents.capturePage(rect)` (no capture permission, §13.6) and scales it to `maxSide` with `nativeImage.resize`. A `region` outside the viewport is rasterized by `doc.render` / `board.render` (§13.3) instead.
  - Marks: the renderer draws on a 2D canvas over the PNG a small numbered badge (14 px at output size, light text on a dark disc with a light ring) at the top-left of each `inView` and `partial` item; overlapping badges move right, then down; an item under 12 px at output size gets no badge and stays in `marks` with `x: null`. The numbers are `view.read`'s `n`, so the model's text and the picture name the same items.
- The model names ids and anchors, never pixels; the app computes the geometry. New commands (write, `undo: 'doc'`, one transaction, needs as `board.items.add`):
  - `board.annotate {boardRef, id, text, anchor: 'right'|'left'|'above'|'below', gap?: 4..200 = 16, point?: {x, y}}` → `{ids}`: a text item, measured as `board.items.add` measures (§6.3), placed on that side of item `id` and moved outward until it overlaps nothing (at most 8 steps), plus a connector to the item; with `point` (0–1000 inside an image item, below) the connector ends at that spot.
  - `board.placeBetween {boardRef, a, b, item}` → `{id}`: `item` without `x` / `y`, centred between the centres of `a` and `b`, moved off overlaps the same way.
  - `connect(a, b)` is `flow.connect` (flowchart plan §7).
- Pixel grounding only for raster content inside an image (a photo or screenshot on a canvas): the client crops that image and asks, in a separate request with `response_format: {type: 'json_schema'}`, for the model's own format. The primary adapter, used by every Qwen tier, reads `{"point_2d": [x, y]}` and `{"bbox_2d": [x1, y1, x2, y2]}`: 0–1000 relative, x first (ms-swift's Qwen3.5 guide and the Qwen3-VL cookbook; the 4B card does not restate it). A second adapter reads Gemma's `{"box_2d": [ymin, xmin, ymax, xmax]}` (0–1000, y first; confirmed only on the 26B-A4B) for the runner-up. Each maps value / 1000 × crop size into the item's box; the point goes to `board.annotate {point}`. Checklist item 12 measures it.

- **Built first: pictures of the selection** (user decision 2026-10-06, SPEC §7i Vision): before `view.render`, a selected canvas, flowchart canvas, image or whiteboard attached in the chat (§13.4 Selection pill) goes to the model as a picture rendered with the export rasterizer (`rasterizeWhiteboard`), at most 1 280 px on the long side, as an OpenAI `image_url` part (a PNG data URL) that llama-server reads with `--mmproj`. Only the message being answered carries it; the history keeps the pill label. No marks yet, and board-item selections and plan charts send text only.

### 13.12 Text rewriting: `text.rewrite`

- `doc.replaceText {path, from, to, text}` (write, `undo: 'doc'`): replaces the block-local offsets `from`–`to` (as `doc.find` returns them) of one text block with plain text, keeping the marks at `from`; one transaction; board nodes refused as by `doc.replace`; `ifRev` honoured. Rewrites and grammar fixes (§13.14) use it; rewording is `write` (§5.2).
- `text.rewrite {text | range, mode, language?}` (write, `undo: 'doc'`, `slow`; needs `doc.open`, `view.editor`, `assistant.ready`) → `{text, paths, warnings?}`.
  - `mode`: `third-person` (first person to third; "I" becomes "the author"), `formal`, `concise` (shorter, same facts), `notes-to-prose` (fragments and bullets to paragraphs, no new facts), `grammar-only` (spelling, grammar and punctuation; no rewording).
  - `range` = `{path, from?, to?}` (one block, default all of it) or `{paths}` (consecutive top-level text blocks). `text` = up to 8 000 characters (a dictation transcript).
  - One model request: thinking off, no tools, the mode's instruction plus the style policy, the keyboard grammar (for `grammar-only` it also allows every character already in the input, so the user's own symbols survive), then the linter (§13.13). `language` defaults to `settings.assistant.language`; the output keeps the input's language.
  - One undo step: a `range` is replaced in place (`doc.replaceText`; for `paths`, one transaction over those blocks). `text` goes in at the caret, replacing a text selection; several paragraphs go in as blocks after the caret's block (§6.1 `at: 'cursor'`). From the dictation pane the caret is the user's: the pane never takes the focus (SPEC §7h).
  - `warnings`: numbers and URLs of the input missing from the output (a deterministic check), and any style flag left by §13.13 (c).
- Entry points: "Rewrite as…" in the dictation pane (a menu of the five modes; rewrites the committed transcript and inserts it at the caret) and palette entries "Rewrite as: …" in a `Writing` group on a document selection.
- New gates (§3.7): `assistant.ready` (subject `assistant` = `{installed, enabled}`; fix "Settings → Assistant → Install") and `doc.textSelection` (a non-empty text selection; the `doc` subject gains `textSelection`).

### 13.13 Plain output rules: keyboard characters, banned patterns

User rules (2026-10-06): no "It's not A, it's B" frames, no "A, B, but C" rule-of-three cadence, no triple-down emphasis, no em dashes, and by default only characters found on a physical keyboard. Three layers:
- (a) **Character grammar** (`settings.assistant.style.keyboardOnly = true`). Plain-text requests (chat replies without tools, `text.rewrite`, the research answer) send a GBNF `grammar` that allows printable ASCII and newline (`root ::= [ -~\n]*`) plus the characters in `style.extraChars` (empty by default; e.g. `£€`, Settings → Assistant → Writing style). JSON requests put the same class as a `pattern` on every string in their schema. Em and en dashes, smart quotes and other symbols cannot be generated. Thinking is off on constrained requests. Tool-call turns are assumed unable to carry a custom grammar, so (c) covers their text arguments. The constraint can cost quality and speed (sampling against a 248–262 K vocabulary): checklist item 13 measures both before it ships on.
- (b) **Style policy** (`style.rules`, an editable list in Settings, each `{id, label, on, example?}`, plus the user's own `style.banned` phrases): contrast frames ("not X, it's Y", "not just X but Y"), rhythmic triplets ("A, B, but C"; three short parallel sentences), stacked intensifiers and repeated emphasis, filler openers ("Great question", "Certainly"), hedges ("It's worth noting", "arguably"), dashes. The enabled rules go into the system prompt as one short list, one bad and one good example each, at most 250 tokens.
- (c) **Linter** `src/app/assistant/style-lint.mjs` (pure, `node --test`) on every generated text: chat replies, rewrites, grammar replacements, and the text arguments of the assistant's write commands (inserted content, item labels, annotations) → `[{rule, from, to, match}]`. Rules: characters outside the set; dashes (`—`, `–`, a spaced ` - ` or `--` between words); regexes for contrast frames, the triplet cadence (three comma-joined phrases of ≤ 4 words closed by "but", "and even" or a full stop, or three consecutive sentences of ≤ 6 words), adjacent intensifiers, the filler and hedge lists and the user's phrases. On a violation, one automatic retry whose message names each violation and its text. Still violating: the fixer changes only what is mechanical (a dash pair → commas, a single dash → a comma or a full stop, `–` in a number range → `-`, smart quotes → straight, `…` → `...`) and flags the rest on the transcript line or in `warnings`. The user's own text and dictation transcripts are never linted.

### 13.14 Live grammar check (local Grammarly)

- Toggle: Settings → Assistant → "Check grammar as I type" (`settings.assistant.grammar = {on: false, model: true, ignoredRules: []}`).
- Trigger: the text block holding the caret, 800 ms after its last change, and when the caret leaves a changed block. Text blocks only (paragraphs, headings, list items, table cells); board labels are not checked.
- Pass 1, Harper (Automattic, Apache-2.0): `harper.js` runs Harper's WebAssembly build in main (Node is not under the renderer's CSP, index.html:5) behind `api.assistant.grammar.check({text, lang})` → lints with spans and suggestions in milliseconds. Harper knows English only (US, UK, Australian and Canadian dialects, from `settings.assistant.language`); other languages go to pass 2 alone. Its version is pinned: the JS API is marked unstable.
- Pass 2, the model, for style and clarity (user decision 2026-10-06, §11 Q11): when the assistant is installed (planned: and `enabled`, its master switch), the pass starts `llama-server` itself if it is not running and wakes it if it sleeps; Harper's issues show meanwhile and the model's follow when it is ready. Each check is a request, so while the user types with the check on, the server stays loaded and sleeps 10 min after the last check (§13.2 Warm-up and idle). On battery the pass is skipped and the check runs Harper alone, since the assistant stays unloaded there (§11 Q15; planned, not the user's words). It runs on the one slot after any assistant turn (a new turn cancels a pending check); thinking off; `response_format` json_schema `{issues: [{quote, replacement, reason, kind: 'grammar'|'clarity'|'style'|'word-choice'}]}`, at most 5; replacements linted (§13.13). Small models miscount characters, so the model quotes the text and the client finds the quote: `from` / `to` = its position; a quote not found is dropped.
- Both passes give `{from, to, replacement, reason, kind, rule, source: 'harper'|'model'}`. `text.check {path}` (read) returns them, so agents use the same check.
- Display: ProseMirror inline decorations (not marks: never saved, exported or undone), a wavy underline coloured by kind, mapped through transactions; an edit inside an issue's range drops it. A hover card (shadcn `popover`) shows the replacement and the reason with **Accept** (`doc.replaceText`, one undo step), **Ignore** (this issue, this session) and **Ignore rule** (adds `rule` to `ignoredRules`; for a model issue its `kind`). Nothing is applied automatically. The palette entry "Next grammar issue" opens the card for keyboard users.
- Cache: issues per `cyrb53(text + lang + passes)`, in memory, 500 entries, least recently used out.
- Latency targets on an 8 GB card: Harper ≤ 50 ms per paragraph, the model pass ≤ 1.5 s for 100 words (checklist item 14).

### 13.15 Web and academic research tools

User decision (2026-10-06, §11 Q10): research needs no API key by default. Facts and papers come from keyless sources and direct fetches; general web search runs in a hidden app browser window and, when a search engine blocks it, in a browser view inside the assistant chat panel where the user browses; paid search APIs are an optional reliable mode.
- Lifetime (user decision, 2026-10-06): the hidden search window and the browser view exist only while in use. The hidden window is created for one search and destroyed when its result is read (or on timeout or Stop); the browser view is created when it opens and destroyed (`webContents.close()`, view removed) when the user closes it, the panel closes, the chat is reset or the app quits. No idle research window, view or timer runs in the background, and nothing survives an app exit: `before-quit` / `will-quit` destroy whatever is still open.
- Off by default: Settings → Research (`settings.assistant.research = {on: false, web: 'browser', sources: {wikipedia, wikidata, arxiv, crossref, europepmc, unpaywall, semanticscholar, openalex}, email: '', jina: false}`; turning research on ticks every keyless source and asks for an optional email, used for Crossref's polite pool and required by Unpaywall; OpenAlex waits for a key). `web` = `'browser'` (the hidden window, then the browser view) | `'tavily'` | `'brave'` | `'exa'` | `'searxng'` | `'none'`. The model gets these tools only while research is on. Other agents get `denied{policy}`: they have their own web tools.
- Commands (read, `slow`; the network runs in main behind `api.research`, sender-checked like `api.agent`); every result record carries `source`, the place it came from:
  - `research.searchFacts {q, source: 'wikipedia'|'wikidata', lang?, count?: 1..10 = 5}` → `[{n, title, url, snippet, qid?, source}]`: Wikipedia's search and page-summary APIs, Wikidata's entity search; `lang` defaults to `settings.assistant.language`. `research.fetch` reads a whole article.
  - `research.searchWeb {q, count?: 1..10 = 5, via?: 'auto'|'view'}` → `[{n, title, url, date?, snippet, source: 'browser'|'view'|'tavily'|'brave'|'exa'|'searxng'}]`. `auto`: the reliable-mode provider when one is set, else the hidden search window (below). `via: 'view'` parses the results page the user has open in the browser view instead (gate `research.view`: a page is open there).
  - `research.searchPapers {q, source: 'arxiv'|'crossref'|'europepmc'|'semanticscholar'|'openalex', count?: 1..10 = 5}` → `[{n, title, authors, year, doi?, url, abstract?, source}]`.
  - `research.fetch {url | doi | view: true, maxTokens?: 300..3000 = 1500}` → `{n, title, site, date?, url, chunks: [{n, text}], source}`. `view: true` reads the page the user has open in the browser view (gate `research.view`; main takes its HTML, nothing is downloaded again) through the same extraction. For `url`, main downloads (https only, ≤ 2 MB, 15 s); the renderer extracts the article with `@mozilla/readability` over `DOMParser` (an inert document: no script runs, nothing loads, and the CSP blocks the network anyway), splits it into ≈ 800-token chunks at paragraph breaks, ranks them by BM25 against the turn's question (`src/research/rank.mjs`, pure) and returns the best within `maxTokens`. A `doi` goes Crossref metadata → Unpaywall's open-access location → arXiv HTML or Europe PMC full-text XML, HTML before PDF; a PDF-only paper returns metadata and abstract with `pdf: true` (PDF text: when a PDF reader is worth its dependency).
  - `research.finish {answer, citations: [n]}` → `{answer, references}`: checks that every `[n]` in the answer names evidence from this turn and that each quoted sentence is a substring of its chunk; a failed check goes back to the model once.
- **Hidden search window** (main; built into Electron, no new dependency): one hidden `BrowserWindow` (`show: false`) in its own persistent session partition (`persist:research`), sandboxed, with no preload and no Node; downloads are cancelled, pop-ups and permission requests denied, and navigation stays on the engine's host. It loads a search engine's plain results page for the query (planned: DuckDuckGo's HTML or lite page); main reads the loaded page's HTML with a fixed script (never model text), and the renderer parses the result links with `DOMParser` and a per-engine selector table, unwrapping the engine's redirect links to their targets. It runs only inside a turn the user started, never in the background, one query at a time, with a minimum gap of a few seconds between queries (planned: 4 s). Best-effort: search engines' terms discourage automated queries and their layouts change, so a page that parses to nothing returns `failed{reason: 'parse'}` and the selector table is fixed in an app release.
- **Browser view** (the fallback): an HTTP 403 or 429, a CAPTCHA or challenge page returns `failed{reason: 'blocked', url}`, and the chat panel offers the browser view: a visible browser embedded inside the assistant chat panel, opened at that results page, in the same `persist:research` session. The user browses and solves any CAPTCHA; the app never solves, skips or works around one, and the model never drives the view: it reads only the pages the user opened, through `research.searchWeb {via: 'view'}` and `research.fetch {view: true}`. A check the user passed keeps its cookie in that session, so later hidden searches may work again; Settings → Research → "Clear research browsing data" empties the session.
  - The view's place in the chat panel is decided (§13.4, §11 Q14 and Q17): the panel widens away from its anchored side, and the view has its address row (planned). It is built with Phase E (§13.7, §12).
- **Reliable mode** (optional, off until the user adds a key in Settings): Tavily (1 000 credits a month free, no card; returns extracted text, saving a fetch); Brave ($5 of free credit a month, a card on file required); Exa ($10 of credit a month); or a self-hosted SearXNG URL (JSON format on, no key). With one set, `research.searchWeb` uses it instead of the hidden window.
- Limits, enforced in main per host: arXiv one request per 3 s on one connection, no PDF re-hosting; Wikipedia and Wikidata one request at a time, with a descriptive `User-Agent` naming the app and, when set, the email (Wikimedia's User-Agent policy); the search engine as in the hidden search window above; Crossref with `mailto` (the polite pool) when `research.email` is set, following `X-Rate-Limit-Limit` / `X-Rate-Limit-Interval` and backing off on 429; OpenAlex only with the user's free key (effectively required since February 2026); Semantic Scholar keyless shares one anonymous pool (unpredictable throttling), 1 request/s with a free key; Unpaywall only with an email (a required parameter); Jina Reader (`r.jina.ai`, keyless, 20 requests/min) only when `research.jina` is on, as a fetch fallback for script-built pages, which sends the URL to Jina. At most 8 research calls per turn, one per round; fetched pages cached per session. Crossref's numeric limits and Europe PMC's could not be verified (research pass of 2026-10-06).
- Safety: public hosts only (a URL that resolves to a loopback, private or link-local address is refused, so `llama-server` and the LAN stay out of reach); evidence goes to the model as quoted data marked untrusted, pages from the browser view included; once a turn has fetched anything or read the view, its tool list drops every write command until the user's next message, so web text cannot drive an edit.
- Keys: typed in Settings, sent once to main, stored encrypted with `safeStorage` in `userData/assistant/keys.json`; the renderer and settings.json hold only `hasKey`. Each outgoing query and URL shows as a transcript line; nothing leaves the device unless the user turned research on, and a paid provider receives queries only once its key is added.

### 13.16 Reasoning quality and safeguards (maths explanations)

The user asked whether a 4B model explains maths well enough (2026-10-06). A research pass answered it and a second pass checked each number against its source; numbers that check could not confirm are left out. Scores are thinking mode and vendor-reported unless marked; harnesses and modes differ, so gaps under ≈ 3 points are noise.

**Verdict**: adequate for school-to-undergraduate explanations ("explain this another way", "walk me through this derivation", "why does this formula hold") with the safeguards below; not a replacement for a frontier model; research-level maths is out of reach. It supports the §11 Q9 switch.
- Qwen3.5-4B (huggingface.co/Qwen/Qwen3.5-4B): MMLU-Pro 79.1, GPQA Diamond 76.2 (reproduced independently: 76.1, code.itp.ac.cn/Lily/scientific-llm-compression-post-training), HMMT Feb 2025 74.0, IFEval 89.8 (instructions such as "explain it for a 12-year-old" are followed), MathVision 74.6 (a picture of an equation or a textbook page works). AIME 2025 85.7 (independent, the same ITP report, 300 samples). MathArena (matharena.ai/models/qwen_qwen3_5_4b): AIME 2026 89.7, HMMT Feb 2026 72.9, ArXivMath 19–38 (research-level problems).
- 2024 frontier models, non-thinking, vendor-reported: GPT-4o GPQA Diamond 49.9–53.1 by version (github.com/openai/simple-evals) and 12 % of AIME 2024 (openai.com/index/learning-to-reason-with-llms); Claude 3.5 Sonnet GPQA Diamond 59.4 (simple-evals). Both had far broader world knowledge and better prose; the 4B pays for its size in facts (Weaknesses).
- Gemma 4 E4B, the runner-up (huggingface.co/google/gemma-4-E4B-it): GPQA Diamond 58.6, AIME 2026 42.5.
- Qwen3.5-9B, the opt-in tier, is within the confidence interval of the 4B on MathArena 2026 (AIME 92.5 ± 4.7, HMMT Feb 71.2 ± 7.7; matharena.ai/models/qwen_qwen3_5_9b): its gain is knowledge (GPQA Diamond 81.7), not competition maths.

**Weaknesses** (each has a safeguard below)
- Invented facts and names: AA-Omniscience accuracy 12.8 %, hallucination rate 80 % (9B: 82 %; artificialanalysis.ai/articles/qwen3-5-small-models). AA defines the rate as incorrect / (incorrect + partial + not attempted): when the model does not know, it gives a confident wrong answer 80 % of the time instead of abstaining. Expect invented theorem names, wrong attributions and made-up "standard results" outside core curricula.
- Arithmetic self-check: "The Validation Gap" (EMNLP 2025, aclanthology.org/2025.emnlp-main.1495) shows small models validate arithmetic through surface consistency and miss simple errors, so "check your work" prompts are unreliable. Indirect evidence: it tested Qwen2.5-1.5B, Llama-3.2-3B and Phi-3-mini, none of them Qwen3.5 or a reasoning model.
- Runaway thinking: on MathArena it writes 27.9 K (AIME 2026) to 46.2 K (ArXivMath) output tokens per competition problem at a 65.5 K cap, 9–15 minutes at ≈ 50 tokens/s (estimate, unmeasured); a trace that hits the cap gives no answer. Liquid AI measured a 22.9 % doom-loop rate (a ≥ 60-character span repeated ≥ 4 times; liquid.ai/blog/antidoom) under greedy decoding on prompts built to cause loops, without Qwen's sampling: evidence that wrong sampling loops, not a general rate.
- Thinking vs non-thinking on hard problems: AIME 2025 ≈ 86 with thinking vs 38 without (third-party card huggingface.co/wflying/Qwen3.5-4B-RL-MATH, settings undisclosed). Without thinking, multi-step derivations are often wrong while reading fluently.
- No benchmark measures explanation quality or teaching, and no MATH-500 or LiveBench score exists for the 4B: the acceptance check below is the only measure.

**Safeguards**
- **Routing per request**: conceptual explanations and rephrasing stay non-thinking (≈ 1–2 K tokens, 20–40 s, estimate). Requests to solve, derive, verify or prove (a keyword check on the message) set `enable_thinking: true`. The chat panel's Thinking menu sets this for the user (user decision 2026-10-06: "make it a selection list, icon remains the same, settings persist"; `settings.assistant.thinking`, SPEC §7i): Auto (default: the keyword check, at 4,096), Off (never, not even for those requests), Low 1,024, Medium 4,096 and High 8,192 tokens of thinking (always), with `max_tokens` = budget + 2,048. Per-request budget (checklist item 8, checked 2026-10-06 in the b11433 source; the server README documents only the flag): `tools/server/server-common.cpp` reads `json_value(body, "reasoning_budget_tokens", json_value(body, "thinking_budget_tokens", -1))` and falls back to `--reasoning-budget` only at -1, so each thinking request sends its budget, a change restarts nothing, and the flag (4,096) stays as the default; `reasoning_budget_message` falls back to the server's `--reasoning-budget-message` ("Thinking budget reached. Give your best answer now."). High at 16 K leaves 6,144 tokens for the prompt, so every budget is cut to `n_ctx` - the last request's tokens (without its reasoning, which is never sent back) - 2,048 (never below 0): later in a chat High thinks less, and its menu line says so. The 16–24 K "Hard problem" option is dropped: it does not fit the 16 K context. Every thinking request sends the card's thinking sampling (temperature 1.0, top_p 0.95, top_k 20, presence_penalty 1.5), never greedy decoding, with `max_tokens` capped above the budget. Issue #22717 (the budget message corrupted the output and looped, builds ≈ b9018–b9033) was fixed by PR #22740 (merged 2026-05-08); the b11433 pin postdates it.
- **Loop guard** (main, ≈ 15 lines in `src/assistant-runtime.js`): on the streamed reasoning, abort when a ≥ 60-character span repeats ≥ 4 times (Liquid AI's definition) and retry once with thinking off.
- **Exact maths tool** `calc.eval {expr, number?: 'BigNumber' | 'Fraction' = 'BigNumber'}` (read, no gates; `expr` ≤ 1 000 characters) → `{value, type}`: one new dependency, math.js (§8), in main behind `api.assistant.calc` (as harper.js, §13.14). It evaluates BigNumber (64 digits) and fraction arithmetic, units and matrices; expressions cannot call `import` or `createUnit` (math.js's security guide); a parse error returns `invalid_args` with math.js's message, so the model fixes the expression. `value` = the formatted result, `type` = `number`, `fraction`, `unit` or `matrix`. The maths system prompt requires every number and simplification in a final answer to come from a `calc.eval` result. Cost: no VRAM, milliseconds per call, one extra prompt round trip per computation (≈ 1–3 s, estimate). Symbolic algebra is skipped until the user asks (§12).
- **Tools and grammar**: maths requests, thinking or not, carry `calc.eval` (plus the §13.15 tools while research is on); thinking maths requests are the one exception to thinking off on tool turns (§13.2 Tool calls). §13.13 (a)'s character grammar runs only with thinking off and tool turns carry none, so maths requests skip the grammar and the §13.13 linter and fixer cover their text; no request is both thinking and grammar-constrained.
- **Cited sources** (§13.15): with research on, definitions and theorem statements come from Wikipedia and Wikidata (`research.searchFacts`; ProofWiki optional later, a MediaWiki API like Wikipedia's) as numbered sources; the maths prompt requires `[n]` on every named theorem, attribution or historical claim, and `research.finish` checks the citations. With research off, the prompt says to state a result without naming or attributing it when no source backs the name. This targets the 80 % guess rate.
- **Self-check, tool-backed**: after a thinking answer, one short non-thinking request with `response_format` json_schema `{claims: [{quote, expr, value}]}` (at most 20) lists the answer's numeric claims; the client evaluates each `expr` through `calc.eval`, compares the result with `value`, finds `quote` in the answer (as §13.14 does) and flags a mismatch inline, never changing the text. The model is never asked to re-read and approve its own numbers (Validation Gap). Toggle `settings.assistant.maths.selfCheck`, on by default for thinking answers; cost ≈ 1.5–2× the answer's latency (estimate).
- **Rendering**: the model writes equations as LaTeX between `$...$` or `$$...$$` (keyboard characters, so the keyboard-only rule holds; the linter skips text inside the delimiters). KaTeX renders them, bundled by esbuild with its CSS and fonts as local files (`default-src 'self'` covers them; no external resource, CSP unchanged). The reasoning (the `reasoning` events of `api.assistant.chat`, §13.2) shows in a collapsible block, collapsed by default, inside the chat panel (layout in §13.4).
- **Escalation, off by default** (`settings.assistant.maths.escalate`): a cloud model at an endpoint the user enters (the 9B, the opt-in tier here before §11 Q19, is now the default, so `'9b'` escalates nothing; Unsloth's list at `3885219` does have an `IQ4_XS`, 5.17 GB, contrary to an earlier note), with the user's own key (in `safeStorage`, §13.15) and the §13.6 warning. It is offered, never automatic, when the budget runs out twice in a turn, the self-check finds a mismatch, or the user asks for a proof or a research-level question; the transcript line names where the request went. Nothing leaves the device unless the user sets this up.
- **Settings**: `settings.assistant.maths = {selfCheck: true, escalate: 'off' | '9b' | 'cloud', cloudEndpoint: ''}`.

**Quantisation** (decided: §11 Q12, `Q6_K` for the 4B; superseded by §11 Q19, 9B `Q4_K_M`, at the end): the research recommends moving the 4B default from `UD-Q4_K_XL` (2.91 GB, ≈ 5.2 GB on the GPU at 32 K) to `Q6_K` (3.53 GB, ≈ 5.8 GB). `Q8_0` (4.48 GB, ≈ 6.8 GB) is too tight on Windows with Electron also on the GPU; `UD-Q5_K_XL` (3.25 GB, ≈ 5.5 GB) if the §13.14 grammar pass needs the room. No KL table exists for the 4B; Unsloth's for Qwen3.5-35B-A3B (99.9 % KLD vs BF16; unsloth.ai/docs/models/qwen3.5/gguf-benchmarks) gives `UD-Q4_K_XL` 0.41, `UD-Q5_K_XL` 0.24, `UD-Q6_K_XL` 0.22 (plain `Q6_K` is not in it). Kaitchup's GGUF tests (9B–397B, no 4B; kaitchup.substack.com/p/summary-of-qwen35-gguf-evaluations) rate Q4 safe; the doubled truncation of thinking traces it reports elsewhere was measured on INT4, NVFP4 and FP8 quants, not GGUF. The user chose `Q6_K` on 2026-10-06. Superseded the same day by §11 Q19: the default is Qwen3.5-9B at `Q4_K_M` (5.68 GB, ≈ 6.9–7.4 GB on the GPU at 16 K before headroom, §13.2 VRAM budget), which Kaitchup's tests cover at Q4; `Q6_K` of the 9B (7.46 GB) does not fit 8 GB with KV and projector, and `UD-Q4_K_XL` (5.97 GB) was passed over for room. The 4B notes above stay for the 4B tier.

**Acceptance check** (with checklist items 6 and 12): 10 of the user's own maths questions through Qwen3.5-4B in both modes and Gemma 4 E4B, safeguards on, rated side by side. No published number gives accuracy targets or the gain of each safeguard; this check is the measure, and a clear loss for Qwen3.5-4B goes back to the user (as item 12).
