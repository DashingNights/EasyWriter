## 0. Summary

**No new engine, no new TipTap node.** A flowchart is a smart canvas (`canvas` node, canvas.js:639-696) whose items include two things the Board does not have yet:

| New | What | Why not something else |
|---|---|---|
| `shape` items grow a **label** (`html`, `size`, `textColor`, `bold`, `align`, `valign`), a **free-angle** `rot` (degrees), and ~30 new **kinds** from a shape registry whose entries carry a polygon (`poly`) | the flowchart node | A separate `node` type would duplicate the shape tool, ribbon, resize rules, tool entries and validation; connectors can bind to *any* item (image, text, canvas too), as in Excalidraw |
| `connector` item: two ends, each **bound to an item + anchor** or a **free point**; routed straight / elbow / curve through absolute waypoints; a head per end; dash; up to three labels (source end, middle, target end), each optional and at its own `t` along the path | the arrow that sticks | A free-box `shape:'arrow'` cannot reference other items (`shapeGeometry` whiteboard.js:264-280 puts its endpoints at padded corners) |

Everything else already exists and keeps its behaviour: in-place editing (`CanvasSession` canvas.js:350-614), smart artboard, multi-selection and marquee, snapping and guides, copy/paste, z-order, one `setNodeMarkup` per gesture = one undo step, autosave, persistent history, export through `itemElement` → `rasterizeWhiteboard` (whiteboard.js:378-424, 2027-2052), rail / ribbon / quick tools / tool search, and the agent `board.*` commands. "Insert flowchart" (§5.1) = pick a library flowchart or New, Synced or Copy, then `insertCanvas` + enter edit mode + the shape tool preset to a flow shape: exactly "auto spawn a smart canvas". Connectors also work on whiteboards (fluid boards) for free.

**One addition outside the canvas: a per-thread flowchart library** (user decision 2026-10-06; §3.8–§3.9, §4, §5.10–§5.11). A library flowchart is a record in `userData/flowcharts/<uuid>.json` that holds one canvas board. The sidebar's Flowcharts tab lists the thread's flowcharts and opens each in a full editor (one fixed `Board` with the usual chrome). In a draft it appears as a **synced canvas** (an ordinary `canvas` node plus `flow: {id, rev}`, drawn live from the record and edited in place by the existing `CanvasSession`, whose commits write back to the library) or as a **copy** (a plain canvas). Still no new node type and no second editor class; in `whiteboard.js` the library needs one line (`cleanItem` drops `flow` from canvas items, made in Phase 0).

**After the fundamentals: prefabs, favourites and shape order** (user decision 2026-10-06; Phase P, §3.10, §5.12). A prefab is a saved copy of selected items. Prefabs belong to the user, not to a thread, and live in `userData/prefabs/<uuid>.json`. A prefab is inserted the way the placement tools insert items. The shape list (`ShapePicker`) gains a Favourites section and a Prefabs section, and its order is kept in settings. A board right-click menu (the installed `DropdownMenu`, opened at the pointer) holds Create prefab… and the existing item actions. Inserted prefab items are plain copies and keep no link to the prefab.

All data logic (shape registry, routing, hit-testing, cloning, alignment, Mermaid, layout adapter) lives in import-free `.mjs` modules under `src/flow/`, tested with `node --test`; `whiteboard.js` gains the gestures and chrome hooks; React gets a few small control components (§5.9).

## 1. Goal and scope

Goal: draw.io / Excalidraw-class flowcharts inside a post, edited in place in the smart canvas, exported to the forum as one image, and fully drivable by AI agents through JSON (graph in, PNG and graph out).

In scope (this plan): shape library with labels and free-angle rotation, sticking connectors with routing, heads, dash, three optional labels (source / middle / target) and waypoints; quick-connect; swimlanes / frames by containment; align / distribute; style presets and style copy; Mermaid import/export; auto-layout (dagre); a per-thread flowchart library with a full editor and synced or copied inserts (§3.8–§3.9, §5.10–§5.11); user prefabs, favourites and a reorderable shape list, with a board right-click menu (Phase P, §3.10, §5.12); agent commands; smoke coverage; SPEC sections.

Out of scope (each with an upgrade path in §12): rotation of items other than shapes, group rotation about the group centre, obstacle avoidance against every shape, draw.io import, canvas-local zoom, a separate flowchart node or surface class, relinking a canvas to another library record, synced canvas items on whiteboards, linked prefabs (editing a prefab does not change the copies already placed).

## 2. User stories

Human
1. I press Ctrl+Alt+F or the Insert flowchart button in the bottom toolbar and pick **New flowchart** (Synced is preselected): the flowchart joins my thread's library and a 1200×675 canvas opens in edit mode with the shape tool on "Process"; I drag boxes, double-click to label them, press **A** and drag from one box to another; the arrow sticks to both and follows them when I move them.
2. I hover a selected box and drag one of its four small arrow dots to make a connected copy or an arrow to an empty spot; a click on a dot clones the box and connects it (Ctrl+Arrow does the same).
3. I drag a segment of an elbow arrow sideways; the bend moves and the rest re-flows. Double-click on the middle of the arrow gives it a "yes" label that moves with it; a double-click near its source end lets me type a "1", near its target end an "n" (draw.io's three labels); I drag each one along the line or beside it.
4. I select several boxes, open Arrange and align them left / distribute vertically; I copy the style of one box and paste it onto others. I drag the round handle above a box to tilt it to any angle (Shift: 15° steps); its arrows stay stuck to the tilted outline.
5. I paste `flowchart LR; A[Start]-->B{OK?}; B-->|yes|C[Ship]` while a canvas is active: the diagram appears laid out; "Copy as Mermaid" gives me the text back.
6. I push the post: the flowchart is one PNG at its document width, identical to what I see.
7. I draw on a whiteboard instead: connectors work the same, and stay inside the board.
8. I open the **Flowcharts** tab at the bottom of the sidebar: my thread's flowcharts are listed (a thread can have many); I open one in the full editor, rename, duplicate or move it, or start a new one.
9. I insert a library flowchart into a draft as **Synced**: editing it in place in the post changes the library flowchart and every other synced place, in this draft or another; Ctrl+Z reverts my edit everywhere. **Copy** gives me an independent canvas; **Unlink** turns a synced canvas into one; **Save to library…** turns a canvas I drew into a library flowchart.
10. I delete a library flowchart that is in use: the confirm says where it is used, and the canvases keep their last picture.

## 3. Concepts and data model

All numbers finite; everything JSON-serialisable (automation conventions #4). Validation in `validItem` (whiteboard.js:72-81) and defaults in `cleanItem` (127-135): a missing optional field is defaulted, never fatal, so every existing draft parses unchanged. `parseBoard` (137-149) stays the single parser; `parseCanvas` (canvas.js:43-52) inherits.

### 3.1 `shape` item (extended)

```jsonc
{ "id": "a1b2c3d", "type": "shape",
  "shape": "diam",                         // ∈ KINDS (registry, §3.5); unknown → item dropped (today's rule)
  "x": 100, "y": 80, "w": 160, "h": 90,    // the box; geometry drawn in viewBox 0 0 w h (as today)
  "color": "#ffffff", "width": 2, "opacity": 1, "fill": "solid", "fillColor": "#3a3b46", "flipX": false, "flipY": false,
  // new, all optional (defaults in cleanItem):
  "rot": 0,                                // degrees clockwise, any angle, normalised to [0, 360) by cleanItem; default 0. x y w h stay the unrotated box; the shape turns about its centre, label included (§3.5)
  "html": "Is it valid?",                  // label; '' (default) = none. Same content rules as text items (plain text + <br>, native <b>/<i>)
  "size": 16, "textColor": "#ffffff", "bold": false, "align": "center", "valign": "middle" }  // label style; align ∈ left|center|right, valign ∈ top|middle|bottom
```

`textColor` defaults to the fixed `'#ffffff'` in `cleanItem` (pure code has no theme). Theme-aware values are chosen only at creation time: the Board (`addText` pattern, whiteboard.js:1145: `pageTheme() === 'light' ? '#111111' : '#ffffff'`) and the agent commands (renderer, current theme). A stored colour never changes with the theme (export must match the editor).

`rot` is a `shape` attribute only (all kinds, `line` and `arrow` included); images, text, strokes, canvases and connectors do not rotate (§12). `validItem`: `rot` finite or absent; `cleanItem`: `((rot % 360) + 360) % 360`, a non-finite `rot` is deleted. No migration: the earlier quarter-turn `rot` (0..3) existed only in this plan's text and was never written to a draft; drafts today have no `rot`.

### 3.2 `text` item (one new optional field)

`h`: the rendered height in board px, written by `Board.commit()` for every text item (`item.h = this.itemHeight(item)`, whiteboard.js:1013-1023). It is a cache for pure code (routing to a text item, `settle()`, tests); `placeItem` (195-201) keeps ignoring it, so text still auto-grows. `validItem`: `h` finite or absent (a bad `h` is deleted by `cleanItem`). Old drafts have no `h`: pure contexts use the estimate `round(size * 1.3 * lines + 12)` with `lines = 1 + count of <br> in html` until the next commit stores it.

### 3.3 `connector` item (new)

```jsonc
{ "id": "k9m2p0q", "type": "connector",
  "from": { "item": "a1b2c3d", "anchor": [0.5, 1] },   // End, bound, fixed anchor: [rx, ry] in 0..1 of the item's box
  "to":   { "item": "z8y7x6w", "anchor": null },       // End, bound, floating: attachment = perimeter projection toward the next point
  // or   { "x": 420, "y": 300 }                        // End, free: board px
  "route": "ortho",                        // 'straight' | 'ortho' | 'curve' (default ortho)
  "corner": 8,                             // ortho only: elbow radius px (0 = sharp); default 8
  "points": [ { "x": 300, "y": 120 } ],    // waypoints, absolute board px, ≤ 32, in path order; same shape for every route
  "heads": { "start": "none", "end": "arrow" },   // HEADS: none · arrow (open V) · triangle · triangle-open · diamond · diamond-open · circle · circle-open · bar · cross · one · many · one-many · zero-one · zero-many · exactly-one
  "color": "#ffffff", "width": 2, "opacity": 1, "dash": "solid",   // dash ∈ solid | dashed | dotted
  "jump": "none",                          // none | arc | gap — opt-in line jumps where this connector crosses others (Phase 3)
  "labels": {                              // draw.io's three labels; every slot optional, {} (default) = none
    "start": { "html": "1", "t": 0.15, "dx": 0, "dy": 0, "size": 14, "textColor": "#ffffff", "bold": false },   // source end
    "mid":   { "html": "yes", "t": 0.5, "dx": 0, "dy": 0, "size": 14, "textColor": "#ffffff", "bold": false },   // middle
    "end":   { "html": "n", "t": 0.85, "dx": 0, "dy": 0, "size": 14, "textColor": "#ffffff", "bold": false } }, // target end
                                           // t: fraction of the path length from the `from` end, 0..1 (defaults 0.15 / 0.5 / 0.85); dx, dy: offset in board px from that path point
  // derived — written by resolveConnectors() (§3.4) on every commit; read by itemElement; never recomputed at render:
  "x": 96, "y": 170, "w": 340, "h": 140,  // bbox incl. heads and labels (so marquee, extent, contentBox, groupBox and the smart artboard work unchanged)
  "d": "M4 0L4 60L336 60L336 132",         // shaft path in bbox px, already shortened by the head lengths
  "tips": [ { "x": 4, "y": 0, "a": -90 }, { "x": 336, "y": 136, "a": 90 } ],   // tip point + tangent angle (deg) per end; headPath(kind, tip, width) draws the heads
  "lps": { "start": { "x": 14, "y": 60 }, "mid": { "x": 176, "y": 60 }, "end": { "x": 336, "y": 62 } } }   // label anchor per present slot in bbox px (path point + dx, dy); {} without labels
```

Rules
- `validConnector(c)` (model.mjs, called from `validItem`): both ends valid (`item` string with `anchor` null or two finite numbers in 0..1, or finite `x`/`y`), enums in range, numbers finite, `points` an array of `{x, y}` objects. `cleanConnector(c)`: fills defaults, caps `points` at 32 (extra dropped), converts anchor names (`'n' 'e' 's' 'w' 'ne' 'nw' 'se' 'sw' 'c'`, agent sugar) to `[rx, ry]`, converts a string `label` (agent sugar) to `labels.mid` with defaults, keeps only the slots `start | mid | end`, drops a slot whose `html` is not a non-empty string, defaults a missing `t` to its slot's default and clamps it to 0..1, defaults `dx`/`dy` to 0, deletes non-finite derived fields.
- Labels are independent: each slot has its own text, style, `t` and offset, and is added, edited, dragged and removed alone (§5.3, §5.4). `t` is a fraction of the path length, so a `start`/`end` label drifts away from its end when the path gets much longer (`// ponytail: a px distance from the end, draw.io's terminal offset, if users ask`).
- **Dangling references** (an end's `item` is not among the siblings) are repaired, never thrown, in `parseBoard` after filtering, in `cleanItem`'s canvas branch (129) and in `resolveConnectors`: (a) the connector has `tips` → that end becomes free at its tip (`{x: c.x + tip.x, y: c.y + tip.y}`); (b) no `tips` and the other end resolves → free end at the other item's centre + 100 px along +x (or the other free point + 100 px); (c) neither → the connector is dropped. Agent writes report (a)/(b) as `warnings: [{code:'dangling', id}]` and (c) as `warnings: [{code:'dropped', id}]` (§7).
- `parseBoard` only repairs references; it does not route. Routing happens in the Board (`render`, `commit`) and defensively in `drawCanvas` / `rasterizeWhiteboard` (§6).

### 3.4 Derived geometry: `resolveConnectors`

`resolveConnectors(items, measure = defaultMeasure, onlyIds = null) → { items, geo }` (route.mjs, pure):
- `items`: a new array; connectors (all, or those in `onlyIds`) get `x, y, w, h, d, tips, lps` rewritten; other items untouched. Each label's path point is `polylinePoint(pts, t)`; its anchor adds `(dx, dy)`; the bbox grows by each label's estimated box (`size`, line count as §3.2).
- `geo`: `Map<connectorId, { pts: [{x,y}…] (board px polyline, curves sampled 16 points per segment), segs: [[p,q]…], tipsAbs }>` for hit-testing, handles, label dragging and marquee. Never stored.
- `measure(item) → {x, y, w, h}`: the **unrotated** box. The Board passes `(i) => ({ x: i.x, y: i.y, w: i.w, h: this.itemHeight(i) })` (text: rendered height; not `itemBox`, which returns the rotated AABB, §5.6); pure callers use the default (`item.h` or the §3.2 estimate). Rotation is applied by route.mjs from `item.rot` (§3.5).

Why derived fields are stored (draw.io stores `sourcePoint`/`targetPoint`, Excalidraw stores `points`): rendering never needs siblings, so the three `itemElement` call sites (`render` 875, `drawCanvas` 209, `rasterizeWhiteboard` 2034) stay one-argument; old files render as saved; an agent reading `board.get` sees where the arrow is. Consistency: `Board.render()` sets `this.items`/`this.geo` from `resolveConnectors`; `Board.commit()` resolves before `host.commit`; the agent path `settle(attrs)` calls the same function; `drawCanvas` and `rasterizeWhiteboard` resolve when any connector lacks a string `d` (O(C), covers unresolved files and skipped `settle`).

### 3.5 Shape registry (`src/flow/shapes.mjs`)

```js
{ kind: 'diam', label: 'Decision', group: 'flow',           // group ∈ 'basic' | 'flow' | 'container'
  path(w, h, inset) → { d, poly },                           // d: SVG path in item px (inset = stroke/2); poly: [[x,y]…] the outline (curves sampled; ellipse 32 pts)
  ports: [[0.5,0],[1,0.5],[0.5,1],[0,0.5],[0,0],[1,0],[1,1],[0,1]],   // default: 4 sides + 4 corners (fractions of the box)
  labelInset: { x: 0.15, y: 0.15 },                          // fractions of w/h the label box is inset by (default 0.08 / 0.08)
  dash: false,                                               // true: dashed outline (frame)
  band: 0,                                                   // container title band height px (lane: 28); label sits in the band
  icon: 'Diamond' | null,                                    // lucide icon name; null → the picker draws path(24, 24, 1)
  keywords: ['decision', 'if', 'branch', 'condition', 'rhombus', 'diamond'],
  mermaid: 'diam', drawio: 'rhombus;perimeter=rhombusPerimeter' }
```

`KINDS` (array, registry order) feeds: `validItem` in whiteboard.js (as built in B1: any `kindOf(shape)`; `SHAPES` stays the picker's 9 kinds, because tools.js `SHAPE_INFO[shape]` and `ShapeControls` list it, until B3's `ShapePicker` and registry-generated tool entries make it `KINDS.map(k => [k.kind, k.label])`), `shapeGeometry` (falls through to `path()` for kinds it does not draw itself), `perimeter(poly, from, toward)` (one generic ray–polygon intersection gives every kind's attachment point and port snapping: no per-kind perimeter code), the shape picker, the tool-search entries, the Mermaid / draw.io adapters.

**Every kind has a `poly`, including the 9 existing ones** (rect, round, ellipse 32 pts, triangle, star 10 pts, thought = its ellipse body, speech = body + tail): without it a connector to a star lands on its box corner. `shapeGeometry` keeps drawing the 9 old kinds' `d`; moving them into `path()` is optional cleanup after the engineers' work lands. Kinds and types without a `poly` (`line`, `arrow`, image, text, canvas) attach on the box (turned by `rot` for the two shape kinds).

`rot` (degrees, free angle): the geometry is drawn for the unrotated box (`path(w, h, inset)` and `shapeGeometry`, unchanged) and `placeItem` turns the whole item element with `transform: rotate(<rot>deg)` about its centre (§6), so outline, fill, label and the editor's handles turn together, as in draw.io and Excalidraw (the label is not kept upright). Pure helpers over the stored unrotated box plus `rot` (≈ 40 lines; Excalidraw's `pointRotateRads` / `polygonIncludesPoint` and Konva's Transformer, both MIT, are the references, ported, not imported, §8):
- `rotatePoint(p, c, deg)` (shapes.mjs); the inverse is `-deg`.
- `rotatePoly(item, poly)` (shapes.mjs): each outline point offset by `x, y` and rotated about the box centre. `perimeter` and port snapping run on it, so attachment points sit on the turned outline. `portPoints(item)` rotates the port fractions the same way; anchors stay fractions of the unrotated box, so a bound end turns with the shape.
- `portNormal(item, anchor)` (shapes.mjs): the outward normal of the anchor's side, rotated by `rot`; the ortho router leaves along the board axis closest to it.
- `rotBox(item)` (shapes.mjs): the axis-aligned bounds of the turned box about the same centre, `w' = w·|cos| + h·|sin|`, `h' = w·|sin| + h·|cos|`. `itemBox` returns it (§5.6).
- `hitTarget(items, p, {exclude, tol, measure})` (model.mjs; as built in B1 it takes no `geo`, connectors are never targets): ports via `anchorPoint`, then an even-odd test of the point against `outlineOf(item)`, the turned outline (equivalent to un-rotating the pointer).
- `resizeInFrame(start, handle, dx, dy, opts)` (model.mjs): the rotated resize of §5.6, pure so Node tests cover it.

### 3.9 Synced canvases: the `flow` attr and the sync rules

- **Attr.** The canvas node (canvas.js:646-655, all `rendered: false`) gains `flow: null | {id, rev}`. `validFlow` (`id` matches the uuid pattern, `rev` an integer ≥ 1, else null) runs in `parseCanvas` (43-52) on HTML parse and wherever canvas.js reads the attr, because drafts load as TipTap JSON without the parser (`mountEditor`, actions.js:280-290). The node's own `w h frame bg items` are the **cache**: a synced node is an ordinary canvas plus `flow`, so drafts stay self-contained, `history.js` dedups its images as today, and export works with the library absent (§6). A **copy** is the same attrs without `flow`. `cleanItem`'s canvas branch (whiteboard.js:164-168) drops `flow` from canvas *items*: a canvas on a whiteboard is never synced.
- **Live view.** `CanvasView.render()` (canvas.js:156-164) draws `liveBoard(view)` = `flowSource.get(flow.id)?.board ?? the node's attrs`, and uses its `w/h` for `aspect-ratio` and `scaleArt`. The constructor calls `flowSource.load(id)` when the record is not loaded and subscribes to `flowSource` (unsubscribed in `destroy`, 266-272); a change of that id, or its arrival, re-renders the view and calls `this.session?.sync()` (canvas.js:415-421), so an open in-place editor follows. `emitCanvas` (107-111) reports the live `w/h`, so the canvas bar's size label is right. `dw` stays per node: two placements may show one flowchart at different widths.
- **In-place edit writes through.** `nodeTarget` (283-305) for a synced node: `attrs()` returns `{...cv.node.attrs, ...liveBoard}`; `commit(attrs, newGroup)` first runs `rev' = flowSource.save(flow.id, pick(attrs, 'w h frame bg items'), {origin: cv})`, then one `setNodeMarkup(pos, {...attrs, flow: {id, rev: rev'}})` (+ `closeHistory` when `newGroup`), as today (291-298). The two steps are one exported function `commitSynced(view, pos, attrs, newGroup)`, which the agent route uses too (§7.1). The store notification re-renders every other view of that id, in this draft or in a draft opened later, and calls `setAttrs` (whiteboard.js:937-941) on the library editor's Board if one is open. The in-place editor of a synced canvas **is** the existing `CanvasSession` (canvas.js:350-614: same Board, rail, ribbon, quick tools, tool search) with a write-through target: the user's "frame-linked full flowchart editor". There is no second editor class.
- **Library edits never dispatch into drafts.** Only views update. Why: history.js `record` restarts the persisted log on any `addToHistory: false` change (history.js:26-27), and `rebuild` (104-129) requires the replayed steps to reach the saved doc (122), so a hidden "refresh the cache" transaction at draft open or on every remote edit would discard the draft's saved undo steps (SPEC §7e). The cache catches up on the node's next own commit (which always writes the live board plus the edit) and on insert, unlink and convert. Between edits made elsewhere the on-disk cache lags; the view and the export (§6) do not. The draft's history records what it records today (the node's own `setNodeMarkup` steps, `flow` a plain attr) and nothing for a remote change, which marks nothing dirty and saves nothing. `// ponytail: cache = own commits only; a no-history refresh at draft open if a stale on-disk cache ever matters (costs that draft's persisted undo log).`
- **`rev`.** `record.rev` is monotonic per record and bumped by every library write in this renderer; `node.flow.rev` is the rev its cache was written with, so a node's cache always equals the library state its `flow.rev` names. The app is single-instance (main.js:486) and every writer lives in one renderer, so `rev` never arbitrates real concurrency; a file edited by hand while the app runs is read at the next launch. New edits: last writer wins. `// ponytail: in-process rev; an ifRev check in flows.save if a second writer process ever exists.`
- **Draft undo/redo of a synced node.** `flows.js` keeps per record, in memory, the chain of this session's library writes `{rev → {pred, origin}}` (origin: the open draft that committed (its id; as built, so a draft's undo after a draft switch or an editor remount still writes back), `'library'` or `'agent'`); a write that restores an earlier state (the write-back below, or the library editor's undo) counts as that state. `CanvasView.update(node)` (232-239; ProseMirror calls it only for a changed node) sees `flow.rev` go from x to y without its own commit (y ≠ `record.rev`). It writes the node's restored board back (`flowSource.save`, a new rev that counts as y) only when the library is at x and every write between x and y came from this draft: an undo walks that stretch back, a redo forward (`writeBackOk(chain, record, origin, x, y)`). Otherwise it writes nothing, and the view keeps showing the live library. Why not "write whenever this draft holds the current rev": the restored cache is the state the node held before the edit, which is older than the library's state at that moment when the cache was stale or another draft, the library editor or an agent wrote in between, so writing it back would drop their edits; and a draft would lose write-back after its first undo, because the node's `flow.rev` lags its own write-back. Ceiling: the chain lives in memory, so after a relaunch a draft's undo of a synced edit reverts only its cache (the view shows the live library); Unlink gives an independent copy.
- **Library editor undo** (the record's own stack in `flows.js`, ≤ 50, in memory): a new rev that counts as the restored state; node caches untouched; views live. `.bak` and trash cover file-level mistakes; history.js `encode/rebuild` is the template if persistence is ever wanted.
- **Unlink** (canvas bar on a synced node; `flow.unlink`): one `setNodeMarkup({...attrs, ...liveBoard, flow: null})` → an ordinary canvas holding the current picture; one undo step (redo re-links). No relink to a different record (insert that one instead).
- **Save to library…** (canvas bar on a canvas without `flow`; `flow.link`): `flows.create({title, threadUrl, board: node attrs})` (title from an `InlineInput`), then `setNodeMarkup({...attrs, flow: {id, rev: 1}})`: a flowchart drawn in place becomes a library flowchart.
- **Duplicate** a library flowchart: a new record (`structuredClone(board)`; item ids only need to be unique within one board), title "<title> (copy)", `rev: 1`; nodes keep pointing at the original. Copying a synced node in the document (Ctrl+C/V on the node selection) keeps `flow`: two live views of one flowchart, as intended. **Rename** and **Move to thread** change the record only; the badge (§5.11) shows the live title.
- **Deleting a flowchart in use.** UI: confirm (AlertDialog, `destructive`) `Delete "Login flow"?`, its description built from `flowRefs` over the open doc and over every other draft (`api.drafts.list()`, then `api.drafts.load(id)` once per draft, as the Gantt plan's `plan.delete` does with `chartRefs`, gantt-kanban.md §8.3): "Used in this draft (2 places) and 1 other draft. Here the canvases become independent copies; elsewhere they keep their last picture and show 'missing'." Then one transaction turns every synced node of that id in the open draft into a copy (`flow: null`, attrs = live board; one undo step, which on undo shows them "missing"), and `api.flows.remove(id)` moves the file to the trash. Other drafts' files are not rewritten: a draft file is never written behind its editor, and `updated` would reorder the sidebar. Agents: `flow.library.remove` asks on every call (§7.1).
- **Missing record.** `flowSource.load(id)` → null marks the id missing: the view draws the cache with the **missing** badge ("Flowchart missing from the library · unlinked view"), the canvas bar offers Unlink, and the in-place editor works on the cache without writing to the library (`commit` skips `flowSource.save` while missing; the node keeps `flow`, so a restored file links back).
- **Not synced**, by design: canvas items on whiteboards, a node's `dw`, the record's `source` (a library field only until Phase 4).

### 3.10 Prefabs and the shape list order (Phase P; `src/flow/prefab.mjs`, `src/app/shape-list.mjs`)

- `makePrefab(items, unit)` (prefab.mjs, pure). (1) `cloneItems(items, seq)` (model.mjs:120): a connector keeps a binding only when both ends are inside the selection; an end bound to an item outside it becomes free at its tip. (2) `moveItem(i, −x0, −y0)` for each item, where `x0, y0` is the top-left of the union of the item boxes (`rotBox` for rotated shapes, the derived bbox for connectors). (3) `scaleItem(i, 1 / unit)` (whiteboard.js:86, exported in Phase P), so sizes are in post px (§6c Units: unit 1 on a whiteboard, 1 / k on a canvas being edited, 1 in the library editor). (4) The derived connector fields `d`, `tips` and `lps` are dropped, so every renderer routes the connectors again (§6 defensive resolve). Every item type is kept: shapes with labels and `rot`, connectors, text, images (data URLs), strokes, and canvas items (only a whiteboard has them). `prefabItems(prefab, unit)` returns `scaleItem(i, unit)` for each item. The Board's insert assigns new ids (`cloneItems` again) and places the items (§5.12).
- `parsePrefab(json)` (pure, never throws) runs the items through `parseBoard`, which repairs dangling ends (§3.3). A `name` that is not a string becomes "Prefab". `keywords` are filtered. `w` and `h` are recomputed from the items when they are not finite. `thumb` is kept only when it is a `data:image/png;base64,` string, else it is null. `summaryOfPrefab(p)` → `{id, name, keywords, w, h, items: n, thumb, created, updated}`.
- Placed items keep no link to the prefab. An insert is a copy, like a paste, so editing, renaming or deleting a prefab never changes a board.
- **Shape list order** is stored in two top-level settings keys, like `draftOrder` / `draftFolders`. `shapeFavourites: [ref]` is the Favourites section in its order. `shapeOrder: {basic?, flow?, container?, prefabs?: [ref]}` holds one array per section, written only after the user reorders that section. `ref = 'kind:<kind>' | 'prefab:<uuid>'`. Section ids are the registry groups `basic | flow | container` (§3.5) plus `prefabs`.
- `src/app/shape-list.mjs` (pure) imports `sortDrafts` / `moveBeside` from draft-order.mjs, which work on any list of `{id}`:
  - `shapeSections(kinds, prefabs, favs, order)` → `[{id, refs}]`. Favourites comes first, and a starred entry shows only there. Entries missing from a section's order come first, as new drafts do, so a new prefab shows at the top of Prefabs. Unknown refs are skipped.
  - `toggleFavourite(favs, ref)` adds the ref at the end or removes it. `moveRef(list, ref, target, after)` moves one ref.
  - `resetOrder(order, section)` deletes that section's array. For Favourites, the reset order is registry order, then prefabs by `created`.
  - `cleanRefs(favs, order, live)` drops refs to deleted prefabs and unknown kinds. It runs before every write, so a dangling ref never survives a change, and `shapeSections` skips such refs in the meantime.

### 5.3 Selected connector
- `renderSelection` (881-893) draws no corner handles for a connector; instead two end handles (`.wb-end`), one midpoint handle per straight segment (`.wb-mid`), and one handle per waypoint (`.wb-wp`). Handles carry `pointer-events: auto` themselves; the connector element keeps `pointer-events: none` (no `.wb-conn.wb-sel{pointer-events:auto}` rule), so a selected connector's large empty bbox never covers the nodes inside it. Hittable parts: the wide transparent hit path (`pointer-events: stroke`, as strokes 403-404), the handles, the label divs.
- Gesture kinds (all through `startGesture / follow / onPointerUp`, 1561-1774, one commit per gesture; gesture state in `g.ends`, `g.wps`, `g.seg`, never `g.points`/`g.path`, which `shiftItems` 996-1002 owns for the pen): `'end'` (drag an end: re-stick / free), `'seg'` (ortho: drag a segment perpendicular → the segment's two endpoints become waypoints moved by the drag, or existing ones move; straight/curve: drag a midpoint → inserts a waypoint there), `'wp'` (drag a waypoint; double-click removes it), `'label'` (drag one label; `g.slot` ∈ `start | mid | end` from the div's `data-slot`; per step `t` = `nearestT(geo.pts, p)` (route.mjs: projection onto the polyline, as a length fraction) and `(dx, dy)` = pointer − `polylinePoint(t)`; released within 8 screen px of the line → `dx = dy = 0`; the other slots do not move). After a `seg`/`wp` gesture, a waypoint within 2 px of the line between its neighbours is removed. "Straighten" clears `points`.
- **Commit detection** (`onPointerUp` 1769-1770 compares `x y w h crop` only): widen to `CHANGE_KEYS = ['x','y','w','h','crop','from','to','points','labels','rot']` compared by `JSON.stringify`, so an end re-stick with an identical bbox is still committed.

### 5.4 Labels (shapes and connectors)

- Connector labels: one `.wb-text` per present slot inside the connector element (`data-slot="start|mid|end"`), centred on `lps[slot]`, `background: var(--wb-bg, transparent)` so it masks the line (§6 sets `--wb-bg`; with `bg: 'transparent'` the line shows through, as in draw.io without label background), each with its own `size` / `textColor` / `bold`.

Double-click on the line: `t` = `nearestT(geo.pts, p)`; the slot is `start` for `t < 0.25`, `end` for `t > 0.75`, else `mid`; an existing label in that slot is edited, else one is added at the clicked `t` (`mid` snaps to 0.5 within 0.1). **Enter** / **F2** on a selected connector edits `mid` (adds it if absent); the Labels popover's Edit button reaches any slot. `startEdit(id, slot)` / `finishEdit` take the slot for connectors (they find `.wb-text[data-slot]` and write `labels[slot].html`); a label left empty removes its slot.

- Rotated shapes: the label wrapper is a child of the item element, so it turns with the shape and is edited turned (contenteditable works under a CSS transform in Chromium).

### 5.5 Quick-connect

- **Style copy / paste**: Ctrl+Shift+C copies the visual keys of the single selected item into a module-level `styleClipboard` (shape: color width opacity fill fillColor size textColor bold align valign; connector: route corner heads color width opacity dash and the size / textColor / bold of each present label slot; text: size color bold align bg; stroke: color width opacity); Ctrl+Shift+V applies the keys the target type has to every selected item (one commit). - **Rotate handle**: a single selected shape shows a round handle `.wb-rot` 24 screen px above its top-edge centre, appended by `renderSelection` (881-893) with the corner handles and sized by `--wb-inv` like `.wb-handle` (180). Gesture `'rotate'` in `startGesture / follow / onPointerUp` (1561-1774): `rot = start.rot + angle(p − c) − angle(p0 − c)` in degrees (`Math.atan2`) about the box centre `c`; **Shift** = 15° steps; normalised to [0, 360); bound connectors re-route live (§6 live path); the ribbon shows the angle while dragging; one commit (`rot` is in `CHANGE_KEYS`). No snapping of the angle without Shift.
- **Rotate commands**: **R** / ribbon button (lucide `RotateCw`): each selected shape's `rot` += 90 about its own centre; one commit. Ribbon angle field (shape branch): shadcn `Input type="number"` (installed, `src/components/ui/input.jsx`), 0–359, step 1, applied to every selected shape. Several shapes always turn each about its own centre (`// ponytail: no group rotation about the group centre; add with the group attribute, Phase 5, if asked`).
- **Resize while rotated** (`resizeItem` 1699-1733): for `rot ≠ 0`, `resizeInFrame` (§3.5) rotates the pointer delta by `−rot` into the item frame, runs today's fixed-corner math on the unrotated box (aspect rules unchanged: Shift on shapes), then re-places `x, y` so the fixed corner keeps its board position (rotate the fixed corner about the old and the new centre and shift by the difference; Konva Transformer approach, ≈ 15 lines). Moving edges do not snap while `rot ≠ 0` (snap lines are axis-aligned; `// ponytail: map the item axes to board axes for quarter turns if asked`) and the `limits()` size cap is skipped; on a whiteboard `clampItem` then pulls the rotated box back inside the bounds.
- **Rotated bounds**: `itemBox` (1026-1028) returns `rotBox(item)` for shapes, so move snapping (`snapLines` 1092-1104 over the gesture's `group` / `boxes`, 1572-1573), the group box (`placeGroupBox` 896-900), marquee (`marqueeHits` 112 on the AABB; generous near 45°, accepted), `contentBox`, the smart artboard, align / distribute and dagre (§8) all see the turned shape. Three places read raw `x` / `w` and switch to `itemBox`: `extent` (1052-1057), `clampItem` (1031-1035: shift `x, y` by the AABB's overshoot) and the canvas frame bound to its one item (`autoSize` 973).
- **Edge handles** (Phase 2): shapes get `n e s w` handles beside the corners (`CORNERS` 18 + `EDGES`); `resizeItem` (1699-1733) zeroes the other axis' delta (in the item frame when rotated) for an edge handle and applies no aspect rule to it. Like the corner handles they are children of the item element and turn with it. Connectors have no resize handles.
- Snapping, guides, grid, marquee, Tab cycling, nudging, z-order, Duplicate, copy/paste: unchanged; connectors take part through their bbox (snap targets use the bbox; a connector's own edges never snap). **Marquee** (`finishMarquee` 1622-1632): non-connectors by `marqueeHits` (112) as today; connectors by `polylineHitsRect(geo.pts, rect)` (route.mjs, pure), never by bbox.

Rules
- Node / edge CRUD stays `board.items.add | update | remove`; the connector, shape-label and `rot` fields go into `ITEM` (`src/app/commands/schema-defs.mjs`, automation plan §3.5), which mirrors `validItem`. `board.items.add` returns `warnings` for repaired ends (§3.3). `board.items.update` merges top-level keys, and `labels` / `heads` per slot (precise edits): `{labels: {mid: {html: 'no'}}}` rewrites the middle label only, `{labels: {end: null}}` removes the target label (a value change, `write`, like shortening text; automation plan §5.2).
- `dryRun` works on every write: the `plan` step returns the transaction (or the graph that would be created) and the executor reports the diff without dispatching (automation plan §3.1 builder style).
- Staleness: `flow.graph.get` and `flow.validate` carry `rev`; writes send `ifRev` → `stale`. No new event: the automation layer's `draft.changed {draftId, rev}` fires on every doc change including diagram edits.
- Errors: envelope codes from the automation plan (`invalid_args`, `not_found` (path or item), `too_large` (> 1000 items or > 1 MB text), `stale`, `busy`, `failed`, `refused`); flow-specific refusals are `refused` with `error.data.code ∈ dangling | unsupported_format | parse_error {line, col} | layout_failed`. Warnings (non-fatal) `code ∈ dangling | dropped | clamped | unknown_kind | lossy` (unknown kind → `rect`, label kept; `lossy {ids, what: 'rot' | 'startLabel' | 'endLabel'}` on export).
- Approval statement: all `flow.*` writes except `flow.library.remove` and `flow.prefabs.remove` (§7.3) are `risk: 'write'` (one ProseMirror step, one library write or one prefab or settings write each, undoable, saved like any edit, never removing an item) and run without a dialog under the default agent policy; none touches `api.forum.*`; `flow.import` from arbitrary text is capped (above) and never evaluates it; the forum is reached only through `push.prepare`, which keeps its human confirm, and Submit stays the human's click.
- **Agent deletes always ask** (user decision): removing board items is `board.items.remove` (or `doc.delete` of the whole canvas block), both `risk: 'destructive'` in the automation plan (its §5.2; §0.1 here): the agent ask (automation plan §5.1) runs on every call, with no "Allow for this session" and nothing remembered, also for a single connector and although the removal is undoable. Several removals in one ask only through `batch`, which lists every destructive step. Connectors repaired or dropped as a side effect of a write (§3.3 rules a–c) are reported as `warnings`, not asked. Deleting a library flowchart is `flow.library.remove`, and deleting a prefab is `flow.prefabs.remove`; both are `destructive` too (§7.1, §7.3). The §0.1 fallback (`window.__agent.flow.*`) has no executor and therefore no ask, so it exposes no remove function.
- Agent guidance encoded in the schema descriptions: give structure (nodes + edges) and let `flow.insert` lay out; address by id; anchors by name; colours from `STYLE_PRESETS`; call `flow.validate`, then `board.render` to look.
- Smoke script (automation Phase 0 `--script`): `test/smoke/flow-agent.json` = `flow.insert(graph) → flow.validate → flow.layout → flow.export(mermaid) → board.render`. Fallback without the registry: `window.__agent.flow.*` (§0.1).

Same module and envelope as above. Prefab and settings writes are `undo: 'none'` unless marked `doc`: prefab files keep `.bak` and a trash, and a settings change is reverted by the inverse command. Every write is a precise edit of one entry per call (automation plan §4.3 #11). `ref` = `'kind:<kind>' | 'prefab:<uuid>'`; `section` ∈ `basic | flow | container | prefabs` (§3.10).

| id | risk / undo | needs | args → result |
|---|---|---|---|

| `flow.prefabs.update` | write / none | — | `{ prefabId, patch: { name?, keywords? } }` → `{}` (the UI's Rename; named like `flow.library.update`) |

- No command edits a prefab's items. To change a prefab, the agent creates a new one and removes the old one (§12).
- `cleanRefs` drops refs to deleted prefabs on the next settings write (§3.10).
- `busy`: as in §7.1, when the target Board has a gesture or a text edit.
- Headless: everything except the thumbnail render needs no window.

## 8. Library choices

## 10. Risks and mitigations

- **Two engineers mid-change in whiteboard.js / canvas.js**: the touch list above is the whole surface. Phase 0 lands as the first commit after their work; the pure modules and tests are independent and can start now.
- **Derived geometry going stale** when attrs change outside the Board (agent `board.items.update`, scripts): `settle()` must call `resolveConnectors` (§0.1 dependency); `render()` resolves in memory as a safety net, so the editor never shows a wrong route and the next commit repairs the file; `drawCanvas`/`rasterizeWhiteboard` resolve unrouted connectors themselves.
- **Text heights in pure code**: stored `h` (§3.2) plus the estimate fallback; a connector to an old text item may be a few px off until the first commit. Accepted.
- **Lost edits on end re-stick, label drag or rotation**: fixed by `CHANGE_KEYS` (§5.3, includes `labels` and `rot`); the smoke acceptance moves a node and asserts the stored `tips` changed.
- **Hit-testing unfilled and rotated shapes**: geometric `hitTarget` over `this.items` (never `elementFromPoint`), un-rotating the pointer first, tested in Node.
- **Rotated resize math**: one pure `resizeInFrame` (Konva Transformer approach) with fixed-corner tests at several angles (Phase 2); edges do not snap while rotated, so no rotated snapping code exists to get wrong.
- **Rotation reaching code that reads raw boxes**: `itemBox` is the one seam (rotated AABB); the three raw readers (`extent`, `clampItem`, the frame binding) are listed and switched in Phase 0; `measure` for routing stays the unrotated box by design (§3.4).
- **Selected connector covering nodes**: no `pointer-events:auto` on the connector element; only hit path, handles and label divs are hittable; marquee by segments.
- **Theme-dependent defaults**: fixed defaults in pure code, theme chosen at creation only.
- **Ortho waypoints under re-routing**: absolute `{x, y}` waypoints (no positional pins); the route always passes through them, so a node moving past the other never invalidates them.
- **html-to-image and SVG**: heads are plain paths (no `<marker>`), dash via attributes, labels are divs with inline styles and `var(--wb-bg)`, rotation is an inline CSS `transform` (html-to-image clones computed styles; its one open transform issue is Safari-only): verified at scale 2 and 4 in the smoke PNGs (the sample has a 30° diamond and a connector with three labels).
- **Keyboard crowding**: A, R, F2, Ctrl+Arrow, Alt+Arrow, Ctrl+Shift+C/V are free on the board today; Alt keyup suppression keeps the menu bar hidden; Ctrl+Shift+C only clashes with Chromium's inspect while DevTools is open.
- **Rail height at 1280×720**: two new slots only (Connector, Arrange); the picker is a popover grid; Auto layout / Import / Export are palette entries. Measured in the Phase 1a checklist.
- **Bundle growth**: dagre (graphlib included) in the single IIFE: 59.7 kB minified measured on 2026-10-06 against the 150 kB budget, re-measured with `--metafile` in Phase 4; fallback layout of our own if exceeded.
- **dagre defects**: pin ≥ 3.1.1 (module-state bug fixed in PR #515); cluster endpoints redirected before layout (open crash, issues #236/#238); `flow-layout` tests cover both.
- **Jump cost**: opt-in per connector, bbox prefilter, 20 000-test cap per resolve with a toast; no raw-pair cap.
- **History file size** for large diagrams: whole `items` per step, existing behaviour, bounded by `historyLimit`; step diffing is a future history.js concern.
- **Shape label vs. text item semantics**: `html` on a shape follows the text-item content rules; `startEdit`'s paste handler (1466) already forces plain text.
- **Whiteboard bounds**: free ends and waypoints clamp through `pointAt`; `flow.layout`/`flow.insert` scale into the board width; clipped head tips at the left/top edge match today's stroke behaviour.
- **Agent writes during a drag**: the automation executor returns `busy` while the target board has a gesture or a text edit (automation plan §3.3 step 7; other boards stay writable); agents retry.
- **Agent deletes**: only `board.items.remove` (and `doc.delete` of the whole block) removes items, only `flow.library.remove` removes a library flowchart, and only `flow.prefabs.remove` removes a prefab; all four are `destructive` and ask on every call (§7, §7.1, §7.3); the pre-registry fallback has no remove function. Agents are not implemented yet, so nothing shipped changes.
- **Library edits wiping a draft's undo history**: a library change never dispatches a transaction into a draft (§3.9), so history.js never restarts a draft's persisted log because of it; the cache catches up on the node's own commits.
- **Stale cache**: the on-disk cache of a synced canvas may lag edits made elsewhere; the view and the export read the live record (§3.9, §6), and C1's smoke sample (a synced canvas with no record) proves the cache path.
- **A draft's undo overwriting newer library edits**: write-back only along a stretch of the chain written by that view alone (§3.9, `writeBackOk`, Node-tested); everything else leaves the library alone.
- **Deleting a flowchart in use**: the confirm names the drafts; the open draft's canvases become copies in one undoable transaction; other drafts keep their last picture with the missing badge; the file goes to the trash with its `.bak`.
- **Large records and lost writes**: 32 MB cap (`too_large`), writes coalesced 300 ms and flushed on save, push, unload, draft switch and workspace close; `.bak` keeps the previous version; a failed write toasts and retries on the next change.
- **Agent writes reaching every draft**: by design for synced flowcharts; the schema says so, `flow.library.get {usage: true}` shows where, and `busy` protects a Board being drawn on (§7.1).
- **Right-click on boards** (Phase P): the board menu replaces Electron's native menu on boards only. A text item being edited keeps the native spelling menu. The menu follows the dismiss-only and one-open rules because it is the installed `DropdownMenu` (§5.12).
- **Large prefabs**: images keep their data URLs, and each prefab is capped at 32 MB (`too_large`). Summaries carry only the ≤ 192 px thumbnail, so opening the picker never loads full prefabs.
- **Stale shape-list refs**: `shapeSections` skips refs to deleted prefabs and unknown kinds, and `cleanRefs` removes them before every settings write (§3.10).

## 11. Open questions for the user

Resolved on 2026-10-06. Q8 by the user's decision (the tab opens the per-thread library); Q1–Q7 by the user's rule "use each plan's stated default"; Q9–Q11 (Phase P) by the same rule. The questions stay listed with their answers.

1. **Obstacle avoidance against all shapes**: Phase 3 avoids only the two bound boxes. Full avoidance = grid A* over every item (~150 lines, slower on big boards) or obstacle-router (a pure-JS libavoid port, LGPL-2.1, 0.1.x; libavoid-js itself is out, its WebAssembly is blocked by `script-src 'self'`). **Answer (default):** two-box avoidance only; full avoidance deferred until a diagram needs it, then own A* (no LGPL).
2. **Snapping on flow canvases**: snap rules are global (`daf-writer.snap`). **Answer (default):** keep them global; no per-canvas grid attr.
3. **Keep the Mermaid source** (`source: {format, text}`) for an agent's regenerate loop (draw.io pattern)? **Answer (default):** yes: one optional canvas attr, and the same optional field on a library record (§3.8); written from Phase 4.
4. **draw.io import**: **Answer (default):** not planned; draw.io export only (Phase 5).
5. **Named style tokens for agents** (tldraw-style `color: 'blue'`): **Answer (default):** none; agents use `STYLE_PRESETS` (§3.6); add tokens only if agents keep producing bad hex.
6. **Type-to-edit a selected shape's label**: **Answer (default):** Enter / F2 / double-click only; the letter tool keys stay.
7. **Canvas-local zoom** for very large diagrams: **Answer (default):** page zoom (≤ 400 %) only; the library editor zooms its own area the same way (§5.10).
8. **Flowcharts tab purpose**: **Answer (user decision):** a per-thread flowchart library with a full editor, and synced or copied inserts (§3.8–§3.9, §5.1, §5.10–§5.11). Flowcharts may now live outside drafts, in `userData/flowcharts/` (§4).
9. **Linked prefabs** (editing a prefab updates every placed copy, as a synced flowchart does)? **Answer (default):** no; an insert is a copy (§3.10).
10. **Prefabs per thread or per user?** **Answer (default):** per user (`userData/prefabs/`), shared by every thread and board.
11. **Where a placed prefab lands**: **Answer (default):** its top-left at the click, as with every placement tool (§6c), not its centre.
